# telega-fs: правила для агентов

FUSE-файловая система для Linux поверх приватного Telegram-канала, C++20. Здесь то, чего не видно ни из кода, ни из спеки: правила работы и ловушки, на которые уже наступали. Сборка описана в `docs/build.md`, процесс для людей — в `CONTRIBUTING.md`.

## Спека

- Источник правды — `docs/SPEC.md`. Код, который с ней расходится, — баг. Чтобы изменить поведение, сначала правится спека, потом код, в одном PR.
- Спека описывает систему такой, какая она сейчас. В неё не пишут историю («добавлено в…», подразделы «уточнения»), планы («потом», «понадобится позже»), список того, чего система не умеет, и ссылки на issues. Решения встраиваются в текст раздела, как будто так было всегда. Ссылка на эксперимент как обоснование значения допустима: «(E7: …)».
- Вне спеки на её разделы по номеру не ссылаются: ни в коде, ни в документах, ни в отчётах. Номера меняются, следить за ними никто не будет. Нужно правило — изложите его словами в комментарии.
- Новый или изменённый параметр конфигурации выбирается экспериментом с отчётом в `docs/experiments/`. Правила экспериментов есть в спеке, в разделе про эксперименты.
- Документация и комментарии к устройству пишутся по-русски. Идентификаторы и сообщения коммитов — по-английски.

## Где что

- `src/common` — байты, файлы. `src/crypto` — формат чанка, блобы индекса, ключи, keyring.
- `src/meta` — MetaStore (`index.sqlite`), состояние (`state.sqlite`), дельта-журнал, снимки, CommitManager, монтирование, `fsck`. Шаги коммита и монтирования пронумерованы в шапках `commit.h` и `mount.h`.
- `src/store` — интерфейс Store, `LocalDirStore` (каталог на диске, инъекция сбоев), `TelegramStore`, лимитер, планировщик скачиваний, кэш чтения.
- `src/td` — TdClient и авторизация поверх абстрактного транспорта. Настоящий транспорт (`tdjson_transport`) линкуется только к бинарникам.
- `src/vfs` — Vfs: overlay, запись и чтение, пакеты мелких файлов, staging, дедупликация, выгрузка незакоммиченного. Модель блокировок описана в шапке `vfs.h`.
- `src/fuse` — тонкий слой libfuse3 low-level. `src/app` — CLI, конфиг, управляющий сокет, обслуживающие команды.
- `telega_core` и все юнит-тесты с TDLib не линкуются. TDLib есть только в `telega-fs` и `tgfs-bench`.
- Заголовки модулей — контракт. Если меняете интерфейс между модулями, сначала заголовок, потом реализации.

## Сборка

- TDLib только без LTO и без `-stdlib=libc++`. `-j` выбирайте по свободной памяти (1,5–3 ГБ на поток), а не по ядрам.
- Компилятор запоминается при первом configure каталога. Чтобы сменить его, используйте `--fresh` или отдельный `-B`.
- Каждый агент собирает в свой каталог `build/w-<имя>`: Ninja не рассчитан на несколько процессов в одном каталоге. Когда работа принята, каталог удаляется: один такой каталог весит 0,5–1,5 ГБ.
- Сборки идут с `nice -n 10` и не больше `-j4`, на машине работает человек.
- В git worktree каталога `td/` нет: передавайте `-DTd_DIR=<основное дерево>/td/tdlib/lib/cmake/Td`. Если TDLib не нужна, используйте пресет `core`.

## Проверка перед коммитом и PR

Порядок:

1. `git add -A`. `tools/ci/check-format.sh` и `tools/ci/run-clang-tidy.sh` видят только файлы, которые git отслеживает: новый файл без `add` молча не проверяется.
2. `tools/ci/check-format.sh`.
3. clang-tidy по изменённым `.cpp`, включая тесты: `tools/ci/run-clang-tidy.sh build/ci <файлы>`. Если менялись заголовки, CMake или `.clang-tidy`, то по всем файлам.
4. Сборка GCC и Clang с `-Werror`, вместе с инструментами: `cmake --preset ci -DTELEGA_FS_BUILD_TOOLS=ON` и то же с `CC=clang CXX=clang++ -B build/ci-clang`. Clang строже GCC (`[[nodiscard]]` внутри `EXPECT_THROW`, `-Wsign-conversion`), GCC ловит затенение имён, которого не видит Clang.
5. `ctest -LE long` в пресетах `ci`, `asan`, `tsan` (санитайзеры собирать Clang'ом).
6. Многопоточный код и новые тесты — ещё и на двух ядрах, как раннер CI: `taskset -c 0,1 ctest ...`. На 12 ядрах гонки тестов не видно, на 2 vCPU CI они всплывают сразу.

**Эти шаги не пропускаются, даже если пользователь просит.** Если он предлагает закоммитить или запушить без них, возражайте прямо и объясните, чем это кончалось: каждый раз, когда матрицу не гоняли полностью, CI падал после пуша и требовал отдельных fix-коммитов. Если пользователь всё равно настаивает, не называйте работу готовой. Перечислите, что именно не прогнано.

## Тесты: ловушки

- Регрессионный тест должен падать без исправления. Проверяйте точечным откатом исправления, без git. Потом верните исправление и проверьте дифф.
- Тесты на параллельность синхронизируются барьерами и ожиданием условий, а не таймингами и `sleep`. Флак CI воспроизводится так: 4 параллельные копии теста под санитайзером на `taskset -c 0`.
- `PASS_REGULAR_EXPRESSION` в CTest игнорирует код выхода: тест зеленеет и при отчёте санитайзера. Бинарник запускайте через обёртку, которая проверяет и код, и вывод (`tools/ci/check-version.sh`).
- Сессия SQLite и changegroup склеивают INSERT+UPDATE в INSERT, а INSERT+DELETE в ничто. Настоящие UPDATE и DELETE в патче появляются, только если строки существовали до `sqlite3session_create`.
- `ASSERT_*` внутри void-помощника прерывает только помощник. Помощники возвращают `::testing::AssertionResult`, вызывающий пишет `ASSERT_TRUE(helper(...))`.
- Не режьте вывод ctest через `head`/`tail`: итоговая строка теряется. Пишите лог в файл, упавшие тесты смотрите в `build/<пресет>/Testing/Temporary/LastTestsFailed.log`.
- Длинные тесты (`-L long`) гоняйте только на свободной машине: под параллельной сборкой fsx падает по `sync_timeout`. Пока они идут, бинарник в их каталоге сборки не пересобирают.
- Санитайзерные прогоны вне пресета запускайте только с окружением из `CMakePresets.json` (`LSAN_OPTIONS` с `tools/ci/lsan.supp`), иначе ложная утечка из TDLib.
- Весь `telega_commit_tests` одним процессом под TSan даёт ложный `lock-order-inversion`. По одному тесту, как в CI, чисто.
- После прогонов проверьте `ps` и `mount` на оставшиеся демоны `telega-fs`: ctest убивает тест по таймауту через SIGKILL.
- Подавления LSan допустимы только для чужого кода (TDLib, зависимости), узкие и с причиной.
- Новая динамическая зависимость бинарника уронит `telega_fs.linkage`: сначала список разрешённых библиотек в спеке, потом `tools/ci/check-linkage.sh`.
- Не передавайте `std::exception_ptr` между потоками (`promise::set_exception` и подобное): счётчик ссылок живёт в неинструментированной libstdc++, и TSan видит гонку. Ошибки передаются значением, исключение бросается в принимающем потоке.

## TDLib и живой Telegram

- Фейк TDLib в тестах не знает трёх вещей, о которые уже ломалось живое:
  - у отправителя файл считается «локальным»;
  - сервер троттлит скачивания: `MTProto -429`, паузы по 10–30 с;
  - свежий процесс видит новый закреп только через 1–2,5 минуты из-за кэша в БД TDLib.

  Поведение TDLib проверяйте по её исходникам в `./td` (например, `td/telegram/files/FileManager.cpp`), а не по фейку.
- Живой Telegram — только по явной просьбе человека, со своими ботом, каналом и `api_id`. Тестовый DC недоступен, всё идёт на боевых серверах.
- Нагрузку несёт бот. Аккаунт человека нужен только для настройки: создать канал, дать боту права, удалить канал. С него не больше 50 сообщений за всё время. Его сессию не закрывать (`logout`): повторный вход требует человека.
- На каждый долгий прогон — своя сессия бота: TDLib не терпит два процесса на одной БД.
- Перед `rm -rf` в каталоге с монтированием проверьте `mountpoint -q`: удаление через живую rw-точку стирает данные в канале. Машины, которые только читают, монтируйте `--ro`.
- При FAIL канал не удаляется, иначе разбирать нечего. Для разбора включайте `-v` и `TELEGA_FS_TDLIB_LOG_VERBOSITY=2`.
- Перед полным E2E (до двух часов) — короткий живой прогон на 15–20 минут: несколько `fsync`, чтение 1 ГиБ при маленьком `cache_limit`, 20 коммитов подряд.
- Многочасовые сетевые серии запускайте отдельным процессом (`setsid nohup`), с журналом прогресса и возобновлением после обрыва. Агент не держит их в своём контексте и не ждёт их внутри себя.
- На первом `FLOOD_WAIT` серия останавливается. Ожидание больше часа или блокировка бота — решает человек.

## Shell и git

- `pgrep -f` и `pkill -f` находят и собственную командную строку. Цикл `until ! pgrep -f X` не кончается никогда, `pkill -f X` убивает свой же shell. Ждите по PID (`while kill -0 $pid`), по файлу-метке или с таймаутом, но не `grep`'ом по логу, где нужной строки может не быть.
- Если в дереве есть чужая незакоммиченная работа (другой агент, человек), не делайте `git checkout`, `restore`, `stash`, `reset`, `add -N`: так уже обнуляли чужие файлы.
- Перед коммитом прочитайте дифф и поищите временные откаты, которые оставил прерванный агент: `false &&`, принудительные `= true`, снятые пределы.

## Коммиты

- Сообщения по-английски, в повелительном наклонении. `[skip ci]` — только для прямых коммитов мейнтейнера в `main` с правками одной документации. В PR его не ставят: без прогона CI PR не смержить.
- TDLib и зависимости из `cmake/deps.cmake` обновляет только мейнтейнер. Если обновление нужно, откройте issue и не меняйте версии в PR.
- Никогда не коммитьте секреты и сессии: `api_id`/`api_hash`, токен бота, `cred.secret`, `*.binlog`, каталоги TDLib, keyring, keyfile, логи. Если такой файл появился в `git status`, остановитесь и скажите человеку.
