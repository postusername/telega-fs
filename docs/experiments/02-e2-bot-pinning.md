# E2. Закрепление в режиме бота

Эксперимент E2 из раздела 17.5 спеки (веха M2, боевые серверы Telegram, режим бота). Инструмент: `tgfs-bench e2 ...` (`tools/bench/tdbench/cmd_e2.cpp`, общий код `exp_common.*`), сырые данные: `docs/experiments/02-e2-bot-pinning/*.csv`.

## Метод

1. `e2 setup`: пользователь создаёт канал (`createNewSupergroupChat`, `is_channel = true`), находит бота по username (`searchPublicChat`) и добавляет его администратором (`setChatMemberStatus`, полный набор прав). Бот убеждается, что канал ему виден (`getChat`).
2. `e2 run`: для каждого набора пользователь меняет права бота (`setChatMemberStatus`), читает их обратно с сервера (`getChatMember`), бот ждёт, пока увидит те же права у себя. Потом 20 циклов: отправка документа, `pinChatMessage`, `getChatPinnedMessage`, `unpinChatMessage` предыдущего закреплённого. Цикл успешен («голова»), если отправка и pin прошли и `getChatPinnedMessage` вернул новое сообщение; «полный» цикл — ещё и unpin без ошибки. Если `getChatPinnedMessage` вернул не то сообщение (или 404), он опрашивается раз в секунду до 75 с, чтобы измерить отставание.
3. Если один и тот же шаг подряд даёт одну и ту же ошибку 3 раза, набор прерывается (экономия сообщений); в таблице это «3 цикла».
4. `e2 run --fresh-only`: бот закрывается, создаётся пустой каталог БД, вход по токену заново, `getChat`, первый `getChatPinnedMessage` (должен вернуть текущую голову), потом те же 20 циклов.
5. Дополнительные пробы (`e2 probe ...`): `getChatPinnedMessage` без закреплённых, удаление бота собственных сообщений, служебные сообщения (перебор id через `getMessages`), как бот с пустой БД узнаёт канал, отставание первого pin.

Наборы прав («по одному» понято как исключение одного права из полного набора; затем кумулятивно уменьшаемые наборы): полный; полный без `manage_chat`, `change_info`, `post`, `edit`, `delete`, `invite`, `restrict`, `promote`, `video_chats`, `stories` (три права историй вместе); только `post+edit+delete`; `post+edit`; `post`; `edit`; `post+delete`. Права `pin_messages` и `manage_topics` отдельным набором не проверялись: у каналов их нет, сервер их отбрасывает (сравнение запрошенных и фактических прав — `e2_rights.csv`).

Вывод: бот с пустой БД знает канал по числовому id (`getChat` проходит за 0,1 с без `access_hash` и без списка чатов; `loadChats` и `getChats` боту недоступны: `400 The method is not available to bots`) и сразу читает голову с сервера. Ограничение на число входов: тут было 3 входа с пустой БД за 13 минут, `FLOOD_WAIT` на входе не было. Перезапуск проверен не на всех 15 наборах: результат определяется правами, а не локальной БД, а входы по токену лимитируются (раздел 17.2).

### Время цикла

Полные циклы без `FLOOD_WAIT`, основной сеанс (220 циклов) и после перезапуска (60 циклов). Сумма отправки, pin, get и unpin без пауз, мс: медиана 427 (342–2196) и 447 (346–8160). Паузы между циклами (12 с) в сумму не входят. Из 280 циклов 4 занимали больше 2 с (редкие задержки сети, не зависящие от набора прав).

Отправка документа ждёт `updateMessageSendSucceeded`, документ 1 КиБ.

### Видимость нового закрепления

`seen_immediately` = первый же `getChatPinnedMessage` после pin вернул новое сообщение: 280 из 280 циклов, где pin прошёл (`e2_cycles.csv`, 295 строк, остальные 15 — прерванные наборы без прав на pin или отправку). Отставание измерено отдельно:

- `e2_first_pin_5cycles.csv`: на только что созданном канале без закреплённых сообщений первый цикл увидел свой pin только через **55,1 с**, остальные четыре цикла (и все последующие) — сразу. В самом первом пробном прогоне (3 цикла, канал уже был удалён, данные не сохранены) на новом канале все три цикла дали `404 Not Found` в течение ~25 с, цикл тогда не опрашивал дальше.
- `e2_lag.csv`: на канале, где уже было закрепление, 6 из 6 новых pin видны сразу (0,0–0,1 с), в том числе с принудительным `getSupergroupFullInfo` каждые 6 с.
- `e2_stale_head.csv`: другой сеанс бота (с пустой БД) сменил голову, пока основной был закрыт; основной сеанс при следующем старте увидел новую голову с первого запроса (4 из 4).
- `e2_first_pin_probe.csv`: на двух новых каналах (в том числе с `getSupergroupFullInfo` до pin) первое закрепление видно сразу, `is_pinned` у сообщения `true` сразу. Отставание 55 с воспроизвелось, таким образом, только в двух случаях из четырёх.

Причина отставания в коде TDLib (`MessagesManager::get_dialog_pinned_message`, `ChatManager::get_channel_full`): голова берётся из кэша `ChannelFull`, а для бота кэш при протухании (60 с) обновляется в фоне и без ожидания. Точное условие, при котором кэш хранит «закреплённых нет» к моменту первого pin, не установлено (вероятно, загрузка полной информации о канале другими вызовами за 60 с до pin, например `getChatMember`). Практический вывод: первый pin в пустом канале может быть невиден вызывающему до минуты.

### Что пишет `getChatPinnedMessage`, если закреплённых нет

`404 Not Found` (текст «Not Found»), на этом канале и на втором новом. Сразу после старта процесса, пока `getChat` для канала не вызывался, любой метод по каналу отвечает `400 Chat not found`, даже если БД канал знает (воспроизведено и для бота, и для пользователя). Значит, «нет закреплённого» надо отличать от «чат не загружен».

### Служебные сообщения

Перебор id 1..661 через `getMessages` (`e2_scan.csv`, `e2_probe.csv`): 1 служебное сообщение создания канала (id 1), 319 документов, **310 служебных сообщений `messagePinMessage` — по одному на каждый pin**, unpin сообщений не порождает; id идут подряд: после создания канала чередуются документ и служебное закрепление (документ, pin, документ, pin...). Два удалённых документа (проба удаления) дают `null`. Служебные сообщения не мешают: голова ищется по закреплённому, чанки адресуются по `msg_id` из индекса. Но каждый коммит занимает **два** серверных id (индекс и служебное закрепление), и для перебора (E3, `gc --deep`, `recover --scan`) диапазон id вдвое шире числа сообщений. Сообщения закрепления отправлены самим ботом, `is_outgoing` у них такой же, как у документов.

### Удаление

Проба `delete`: бот с правами `post+edit` и бот с `post+edit+delete` удаляют собственное сообщение (`deleteMessages`, `revoke = true`) успешно, `getMessages` затем возвращает `null`. Права удаления для собственных сообщений не нужны. Удаление чужих сообщений в E2 не проверялось: у пользователя нет отправленных сообщений (лимит 50 берегли для E3), поэтому рекомендация «давать удаление» основана на документации Telegram, а не на замере.

### Другие находки

- Unpin сообщения, которого нет в памяти процесса (пустая БД, `use_message_database = false`), даёт `400 Message not found`; после `getMessages` по этому id unpin проходит (4 из 4 проб в `e2_probe.csv`). В циклах после перезапуска unpin проходил, потому что первый `getChatPinnedMessage` уже вернул, и тем самым загрузил, это сообщение.
- Права в канале: `can_pin_messages` у канала не действует (pin и unpin требуют `can_edit_messages`, как и сказано в описании `unpinChatMessage` в схеме).

### FLOOD_WAIT

| Прогон | Интервал между циклами | Что произошло |
|---|---|---|
| первый | 3,1 с | на 8-м цикле `FLOOD_WAIT 37 с` на отправке (в канале на тот момент 7 циклов ≈ 21 действие за ~25 с) |
| второй | 8 с | на 10-м цикле `FLOOD_WAIT 12 с` на unpin (≈ 22 действия в минуту) |
| основной и с пустой БД | 12 с | 0 событий за 295 циклов основной серии и 20 циклов проб |

В обоих случаях ожидание с запасом (×1,2 + 5 с) отработал инструмент, потом прогон был остановлен мной и перезапущен с большим интервалом; данные прерванных прогонов лежат в `e2_flood_run1_pace3s.csv` и `e2_flood_run2_pace8s.csv`. Вывод: лимит считает **pin и unpin наравне с сообщениями**, один коммит стоит три действия (отправка индекса, pin, unpin). Ближе к границе, чем в разделе 10.2 («20 сообщений в минуту»): для бота на канале это ориентировочно 20 действий в минуту. Значение уточнит E5. Один 429 дал и перебор `getMessages` пачками по 100 подряд (`retry after 30`, при первой попытке без пауз), это пригодится в E3.

## Что сделано и не сделано

Сделано: все пункты метода раздела 17.5, кроме перезапуска для всех наборов прав (три набора, см. выше) и проверки прерванных наборов на все 20 циклов (3 цикла, ошибка детерминирована). Бот отправил около 330 документов (в том числе 20 в двух прогонах, остановленных `FLOOD_WAIT`, и около 15 в пробах), сделал 310 pin-ов (по ним 310 служебных сообщений); пользователь отправил **0** сообщений и сделал порядка 75 вызовов API настройки (создание канала три раза, добавление бота, смена и чтение прав, удаление). Канал удалён по окончании.

## Правки спеки (предложение)

1. **Раздел 10.3 (бот).** Права бота в канале: «публиковать, редактировать и удалять; минимум для работы — публиковать и редактировать, потому что pin и unpin в канале требуют `can_edit_messages` (права `can_pin_messages` у каналов нет)». Убрать «минимальный набор определяет E2», записать результат. Запасной вариант с `setChatDescription` удалить.
2. **Разделы 2 и 7.1.** Оговорка к строке про `getChatPinnedMessage`: «в режиме бота `getChatPinnedMessage` отдаёт кэш TDLib, который может не содержать собственный первый pin до минуты». В шаге 4 (CAS) для бота: если локально записана голова `H` и `getChatPinnedMessage` вернул `404` или другое сообщение, а последний собственный pin был менее 90 с назад, повторять опрос, а не переходить в read-only. После перезапуска процесса голова читается с сервера с первого запроса, при старте проблемы нет.
3. **Раздел 7.1, шаг 7.** `unpinChatMessage(H)` после перезапуска процесса требует, чтобы сообщение `H` было загружено в TDLib: сначала `getChatPinnedMessage` (возвращает его) или `getMessages`, иначе `400 Message not found`.
4. **Раздел 10.1.** После старта процесса и перед первым запросом по каналу вызвать `getChat(chat_id)`: без этого все методы отвечают `400 Chat not found`. Боту хватает числового id даже на пустой БД, пользователю — `loadChats`, потом `getChat`.
5. **Раздел 4.** Уточнить: каждый pin создаёт в канале служебное `messagePinMessage` (по одному на pin, unpin не создаёт), оно занимает серверный id, поэтому каждый коммит расходует два подряд идущих id; диапазон перебора в E3 и `gc --deep` надо считать с учётом этого. Сейчас «закрепления игнорируются» верно, но без этого пояснения.
6. **Разделы 10.2 и 17.8 (E5).** Pin и unpin считаются в лимит наравне с отправкой (`FLOOD_WAIT` 12 и 37 с на 22 и 21 действии в минуту): `send_rate` для бота считать в действиях, коммит — 3 действия. Значение в E5 мерить вместе с pin и unpin.
7. **Раздел 17.5, итог.** Добавить итог по образцу E1: головa — закреплённое сообщение, 20 из 20 в том числе после перезапуска; минимальные права `post+edit`.
8. **Раздел 17.2.** В правила экспериментов: «лимит считает pin и unpin; в сериях с pin держать не больше 15 действий в минуту».

## Грабли TDLib для следующих экспериментов

- После старта процесса `getChat` перед любым методом по каналу (E3, E5, E6).
- `getChatPinnedMessage` без закреплённых — `404`, не пустой ответ.
- `getMessages` для удалённого или ещё не существующего id возвращает `null` в массиве (а не ошибку), для E3 это важно; пачки по 100 подряд без паузы дают 429 `retry after 30`.
- `deleteChat` у пользователя иногда отвечает `400 Chat not found` сразу после старта процесса: нужен повтор после `getChat`.
- Права `can_manage_chat` сервер включает сам для любого администратора канала; убрать нельзя.
- Бот на канале шлёт и pin-ы как сообщения: считать их в лимит.
