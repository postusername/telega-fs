# E4. Скачивание диапазонов

Эксперимент E4 (веха M2, боевые серверы Telegram, только режим бота). Инструмент: `tgfs-bench e4 ...` (`tools/bench/tdbench/cmd_e4.cpp`, общий код `exp_common.*`), сырые данные: `docs/experiments/04-e4-range-download/*.csv`.

**Статус: завершён.** Проверка `remote_file_id` через 24 часа выполнена 2026-11-20 18:56 UTC (возраст документа 24,06 ч), строки в `e4_check24.csv`. После неё канал E4 удалён (`e4 teardown`).

## Метод

1. `e4 setup`: пользователь создаёт канал и добавляет бота; бот заливает документ 512 МиБ, сообщение и `remote_file_id` сохраняются в `<state-dir>/e4.json` (вне репозитория, права 0600), вместе с seed, размером и временем загрузки. Исходный файл удаляется: ожидаемое содержимое любого диапазона считается по seed. Сразу после загрузки в том же сеансе: `getRemoteFile` (тот же `file_id`, 0,7 мс).
2. `e4 run`, три варианта сеанса бота:
   - `main` — основная БД бота (файл известен TDLib с момента загрузки, локальная копия удалена);
   - `fresh` — перезапуск с пустой БД: новый каталог, вход по токену, `getRemoteFile`, `getChat`, `getMessages`;
   - `fresh-remote-only` — то же, но `file_id` только из `getRemoteFile`, без `getMessages`.
3. Каждый замер: `deleteFile` (сброс локального состояния), подписка на `updateFile`, `downloadFile(file_id, priority 1, offset, limit, synchronous = true)`, `readFilePart(offset, count)`, сверка с данными по seed, затем `getFile` (`downloaded_size`, `downloaded_prefix_size`, `download_offset`, `st_size` и `st_blocks` файла на диске), прямое чтение того же диапазона по `local.path`.
4. Диапазоны: «начало, середина, конец» двух форм. Выровненная (`aligned64k`): смещения 0, 256 МиБ, `размер − 64 КиБ`, длина 64 КиБ. Форма сегмента зашифрованного чанка (`segment`, формат зашифрованного чанка): смещение `40 + i·65552`, длина 65552 (начало, середина, последний сегмент до конца файла). Повторов по 5 (сетевые замеры, минимум 5 повторов), порядок: повтор 1 по всем шести диапазонам, повтор 2 и так далее. Дополнительно: хвост с `limit` 1 МиБ (больше остатка), диапазоны 1, 4 и 16 МиБ из середины (по 3 повтора), 16 соседних диапазонов по 64 КиБ подряд без сброса между ними (как readahead).
5. `getRemoteFile` и `getMessages` как способы получить `file_id`: сразу после загрузки, после перезапуска с пустой БД; скачивание начала по `file_id` из `getMessages`.
6. `e4 check24`: то же через сутки (выполнено, возраст 24,06 ч).

### Скачано на самом деле

Все числа — `local.downloaded_size` после `downloadFile` и размер на диске (`st_blocks`) совпали во всех замерах, `st_size` локального файла равен полному размеру документа (разреженный файл), `is_downloading_completed = false`. Данные в `e4_ranges.csv` (колонки `downloaded_size`, `prefix_size`, `disk_size`, `disk_alloc`).

- **Размер известен** (файл получен как в `main` и `fresh`): запрос 64 КиБ скачивает 256 КиБ (части 256 КиБ с выравниванием), запрос сегмента 65 552 байта скачивает 256 КиБ или, если он пересекает границу части, 512 КиБ. Диапазоны в 1, 4, 16 МиБ скачиваются точно. Читать 64 КиБ случайно — это 4-кратная лишняя загрузка, а последовательное чтение этого не платит: внутри уже скачанной части следующие 64 КиБ готовы за 0,5–0,9 мс, новая часть стоит один запрос (таблица ниже).
- **Размер неизвестен** (`fresh-remote-only`): части 64 КиБ, скачано ровно запрошенное (65 536 или 131 072 для сегмента), поэтому последовательное чтение платит запрос на каждые 64 КиБ.
- **Хвост с `limit` больше остатка** (запрос последних 64 КиБ с `limit` 1 МиБ, размер известен): данные верны, но TDLib скачал 1 310 720 байт (1,25 МиБ), хотя до конца файла оставалось 64 КиБ. Причину не выясняли; на практике надо ограничивать `limit` остатком файла.

Последовательное чтение: 16 соседних диапазонов по 64 КиБ из четверти файла без сброса между ними (`e4_sequential.csv`):

|---|---|---|---|
| main | 0,5 (0,4–0,7) | 407 (192–483) | 1 МиБ |

В `main` первый запрос части заметно дороже (407 мс), вероятно из-за первого обращения сеанса к DC (как и первый повтор выше), причина не проверялась. Выравнивание по границам частей 256 КиБ даёт readahead даром: 16 подряд идущих чтений по 64 КиБ укладываются в 4 запроса к серверу вместо 16.

## Выводы по критериям эксперимента

1. Частичное скачивание работает, TDLib не качает файл целиком: **модель чтения диапазонов не пересматривается, ограничение `chunk_size ≤ 8 МиБ` в E7 не добавляется.** Цена чтения 64 КиБ — около 0,1 с на запрос и 256 КиБ трафика, независимо от размера чанка.
2. `remote_file_id` за первый час не протух, в том числе после перезапуска с пустой БД. Через 24 часа то же самое. Но на пустой БД результат `getRemoteFile` непригоден для чтения хвоста файла, поэтому **путь через `getMessages` становится основным после перезапуска (и при любой неизвестной TDLib записи), а `getRemoteFile` — оптимизацией для файла, уже известного TDLib (размер больше 0).**

## Что приняли по итогам

1. **Получение `file_id`.** Если TDLib знает файл (`getFile` или `getRemoteFile` вернул размер, равный размеру чанка из индекса), берётся он. Иначе, и после любой ошибки скачивания, — `getMessages(chat_id, [msg_id])`, берётся `content.document.document.id` и обновляется `remote_file_id`. Причина: на пустой БД `getRemoteFile` отвечает успехом с размером 0, и скачивание конца файла падает (`400 File download has failed or was canceled`), поэтому запасной путь «при неудаче `getRemoteFile`» не сработал бы вовремя.
2. **Чтение диапазона.** `limit` у `downloadFile` не превышает остаток файла. Выравнивать зашифрованный диапазон до границ частей TDLib (256 КиБ при известном размере) нет смысла, но надо помнить, что 64 КиБ качаются как 256 КиБ. Скачанное предпочтительнее читать из `local.path` напрямую (`pread` по тем же смещениям, он верен: 117 из 117 завершившихся замеров). `readFilePart` остаётся запасным путём для диапазонов до 1 МиБ: 16 МиБ через него занимают 1,9 с.
3. **Readahead.** Последовательные чтения внутри 256 КиБ почти бесплатны (0,5–0,9 мс), новая часть — один запрос около 100 мс. Параметры readahead (4 МиБ с удвоением до 32 МиБ) оставались предварительными: оптимум определяли E7 вместе с E5 (скорость 12–15 МиБ/с на этом канале связи), потом проверил E10.
4. **Итог E4.** Частичное скачивание работает, `chunk_size` не ограничивается, `getMessages` — основной путь после перезапуска, через 24 часа `remote_file_id` по-прежнему работает.
5. **Старт клиента.** Перед `getMessages` и `getRemoteFile` для канала вызывается `getChat(chat_id)` (см. E2).
6. **Выравнивание сегмента.** Сегмент чанка не выровнен по 64 КиБ (смещение `40 + i·65552`), поэтому его чтение иногда пересекает границу части TDLib и качает вдвое больше (512 КиБ вместо 256). Это приемлемо; если бы измерения E7 показали, что это важно, заголовок можно было бы дополнить до 64 КиБ. Формат не менялся.

## Что не сделано

- Режим пользователя не мерялся (правило экспериментов: нагрузка только у бота).
- Скорости скачивания на другом канале связи, параллельных скачиваний и `download_concurrency` не мерили (это E7).

## Грабли TDLib для следующих экспериментов (E3, E5, E6)

- `getRemoteFile` на пустой БД возвращает размер 0 и ломает скачивание конца файла: для E3 (`getMessages` по id) это означает, что файл надо брать из сообщения; E5 и E6 работают на отправке, но загрузка 512 МиБ одним документом прошла без ошибок за 33 с.
- Локальный файл при частичном скачивании разреженный полного размера (`st_size` равен размеру документа): кэш `tdfiles/` надо считать по `st_blocks`, а не по `st_size` (параметр `cache_limit`, кэш чтения).
- Часть скачивания 256 КиБ (64 КиБ, если размер неизвестен): плотная случайная работа по 64 КиБ — 4-кратный трафик.
- `readFilePart` отдаёт данные через JSON и base64: для диапазонов в мегабайты и больше медленнее самого скачивания.
- Файл, отправленный этим же сеансом, в его БД числится локальным (путь удалённого исходника): чтобы замерять скачивание, надо `deleteFile` или пустая БД.
