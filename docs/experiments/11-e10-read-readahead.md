# E10. Чтение и readahead

Эксперимент E10 из раздела 17.13 спеки (веха M3, боевые серверы Telegram, только режим бота). Инструмент: `tgfs-bench e10 ...` (`tools/bench/tdbench/cmd_e10.cpp`, прототип планировщика скачиваний `tools/bench/tdbench/read_sched.h`, общий код `exp_common.*`, `run_common.*`, шифрование чанков `src/crypto/chunk.*`), сырые данные: `docs/experiments/11-e10-read-readahead/*.csv` (пробный прогон — в `probe/`).

**Статус: завершён.** Полный прогон: 95 серий из 95 прошли с первой попытки, 0 `FLOOD_WAIT`, 0 сетевых ошибок, 0 расхождений данных (кроме замечания про устаревший путь в пункте 3, там данные верны).

## Метод

Один фоновый процесс (`<state-dir>/tgfs-bench-e10 e10 run`, возобновляемый, flock на сессию, SIGTERM сохраняет состояние). 5 кругов, в каждом по одной серии каждого варианта: p1 (3 варианта), p2 (3), p3 (2), p4, p5 (3), p7 и p6 (6 вариантов окна, порядок вращается по кругам, чтобы время суток не смещало один вариант); пауза между сериями 5 с. Перед каждой серией кэш TDLib очищается: `deleteFile` и проверка, что `downloaded_size` равен 0, а файла на диске нет (пункт 6 проверяет 32 документа, 960 проверок за прогон, при неудаче серия падает; таких не было). Все скачивания — `downloadFile` с `synchronous = false`, кроме тех мест, где проверяется судьба синхронного запроса (пункты 2, 5, 7). Ход замеряется по `updateFile` с меткой времени прихода.

- **Пункт 1.** Четыре файла (группа из 4 документов, по кругам разные) стартуют подряд с приоритетами 1, 8, 16, 32 (`asc`), 32, 16, 8, 1 (`desc`) и 16 × 4 (`equal`). Порядок завершения, момент первого байта и объём, который к первому завершению успели получить остальные.
- **Пункт 2.** Три файла (B, C, D) с приоритетом 8, затем A с приоритетом 1 синхронным запросом (его исход ловится отдельным потоком). Через 300 мс режим `raise`: `downloadFile(A)` с теми же `offset` и `limit`, приоритет 32, `synchronous = false`; `raise_sync`: то же, но синхронный; `control`: ничего не делать.
- **Пункт 3.** Скачивание с `offset` 0 (`from0`) и с `offset` = начало 48-го сегмента (`from3m`, 3 МиБ), `limit` 0. На каждом апдейте целые сегменты внутри `[download_offset, download_offset + prefix)` читаются `pread` по пути из апдейта, расшифровываются (проверка тега) и сверяются с данными по seed. Для `from3m` скачивание «до конца» не завершается флагом, конец определяется по префиксу. Основной прогон читал по пути из апдейта без повтора, поэтому устаревший путь давал ложные «расхождения» (3 сегмента). Проверка пункта 3 повторена с повтором по свежему пути TDLib: `e10_p3_recheck.csv`, колонка `unreadable_stale_path`.
- **Пункт 4.** Файл X скачан целиком, файл Y только `[0, 4 МиБ)`. По 100 вызовов на каждую операцию, диапазон 128 КиБ открытого текста (два сегмента, `2 × 65 552` байт) в случайном месте (seed `0xE10A4 + повтор`): `getFileDownloadedPrefixSize`, `pread` (дескриптор открыт заранее), `downloadFile` синхронный (приоритет 16). Для Y ещё 100 вызовов `getFileDownloadedPrefixSize` за пределами скачанного (всегда 0). Трафик за 100 `downloadFile` — по `getNetworkStatistics`.
- **Пункт 5.** `downloadFile(A, 0, 8 МиБ)`; когда скачан 1 МиБ — `downloadFile(A, 6 МиБ, 1 МиБ)`. Варианты: `sync` (оба синхронные, исход прежнего ловится потоком), `async` (оба `synchronous = false`), `extend` (прежний запрос `[0, 4 МиБ)` синхронный, новый тот же `offset`, `limit` 0, то есть продление окна). После завершения нового запроса 3 с наблюдения за `downloaded_size` (докачивает ли TDLib прежнее окно) и сверка данных сохранённой и новой частей.
- **Пункт 6.** Прототип `ReadScheduler` и `ChunkReader` читает 256 МиБ (32 чанка) кусками по 128 КиБ подряд. `ChunkReader`: последовательность по концу предыдущего чтения (допуск в окно), окно удваивается при каждом попадании до `wmax`, на каждый чанк один запрос диапазона с приоритетом `16 − расстояние в чанках`, перед ожиданием данных; ожидание, `pread`, расшифровка сегментов; сверка с seed идёт вне замера. Планировщик: правила раздела 8.2 (один активный запрос на файл, проверка готового, ожидание покрывающего активного с повышением приоритета, вытеснение, захват остатка, очередь readahead, не больше `download_concurrency` = 4 активных и не больше 2 из них readahead) и **продление** окна readahead (тот же `offset`, больший `limit`), которого в спеке нет. Окна: без readahead, 4, 8, 16, 32 МиБ и 4 → 32 МиБ. Скорость считается по времени без сверки. Время до первого байта — задержка первого чтения серии (включает проверку у TDLib и первый `downloadFile`).
- **Пункт 7.** Серия готовит файлы X (целиком), Y (`[0, 3 МиБ)`), Z (целиком), W1 (целиком) и W2 (`[0, 3 МиБ)`), записывает состояние, проверяет `deleteFile` на W1 и W2 (`st_blocks` и размер `files/`), закрывает клиент, удаляет файл Z за спиной TDLib и запускает **дочерний процесс** `tgfs-bench e10 restart-check` с той же БД: `getRemoteFile`, префиксы, чтение X и Y, повторные `downloadFile` с замером сети, повторное скачивание Z, затем документ U: скачан, файл удалён при работающем TDLib, скачан снова.

Серия «чистая», если завершилась без ошибок; все 95 серий завершились с первой попытки. Повтор серии на ошибку (до 3 раз) и ожидание `FLOOD_WAIT` предусмотрены, не понадобились.

### 1. Приоритет между файлами

Медианы времени завершения по 5 повторам (по рангу завершения), мс; файлы по 8 МиБ, четыре сразу.

| `desc` (32, 16, 8, 1) | 689 | 1282 | 1874 | 2470 | 32, 16, 8, 1 (5 из 5) | 0,06 (0,06–0,19) |

Файлы идут по одному: интервалы между завершениями 0,6 с, то есть время одного 8-МиБ файла на скорости одного потока (13 МиБ/с). Лишние 2 МиБ у остальных к первому завершению — части, уже ушедшие в сеть до прихода более приоритетного запроса (в `desc` они стартуют позже и их нет). Одна серия `equal-r2` задержалась на третьем и четвёртом файле (3471 и 3820 мс), порядок не изменился.

## Выводы

Модель чтения раздела 8.2 и приоритеты раздела 10.2 подтверждены целиком. Опровергнуто одно число (стоимость лишнего `downloadFile`), а в поведение TDLib нужно внести пять уточнений:

1. TDLib исполняет скачивания по приоритету по одному: пересчёт приоритетов повторным `downloadFile` с теми же `offset` и `limit` работает, ограничение числа пользовательских скачиваний (запасной вариант 10.2) не нужно.
2. Прежний синхронный запрос при смене `offset` или `limit` отменяется, но в асинхронном режиме отмены не видно вообще. Планировщик, работающий только с `synchronous = false`, отмены не получает.
3. Продление окна тем же `offset` и большим `limit` не прерывает скачивание, поэтому окно readahead в пределах одного файла можно вести одним скачиванием, а не цепочкой запросов.
4. Прежнее окно после вытеснения не докачивается и первый байт нового окна приходит через ~0,3 с. Правило «`limit` захватывает остаток вытесненного окна» оправдано.
5. `local.path` меняется при завершении. Состояние «скачано» нельзя читать по `is_downloading_completed` и `local.path`: после перезапуска и удаления файла за спиной TDLib они показывают завершённое скачивание, а `getFileDownloadedPrefixSize` отвечает 0. Скачивание «до конца файла» не ставит `is_downloading_completed`.

Практическая скорость упирается в поток TDLib (около 14 МиБ/с), readahead превращает чтение в сплошную загрузку (14–17 МиБ/с против 0,96) и держит задержку чтения в единицах миллисекунд, p99 около 60–85 мс (против 252 мс). Значения `readahead` = 4 МиБ и `readahead_max` = 32 МиБ из спеки остаются.

Ограничения: окна больше 32 МиБ и поведение при остановке чтения посреди окна (лишний трафик) не меряли. Сеть и сборка Debug описаны выше. Скорость одного потока зависит от сети; вывод про 32 МиБ следует из разницы около 2,5 МиБ/с: диапазоны повторов 13,5–14,6 МиБ/с (окна 4–16 МиБ) и 16,0–17,1 МиБ/с (32 МиБ) не пересекаются.

## Грабли TDLib и инструмента

- **`local.path` меняется при завершении**: временный путь, затем итоговый. Стороннее чтение по сохранённому пути после завершения даёт `ENOENT`, это дало ложные «расхождения» в первой версии пункта 3.
- **`limit` равный 8 МиБ не совпадает с размером файла 8 390 696 байт**: скачивание останавливается на 8 388 608 байт, `is_downloading_completed` остаётся 0, ожидание завершения по флагу зависает (в пробе это был вариант `extend`). Для «до конца» нужен `limit` 0.
- **Счётчики `getNetworkStatistics` обновляются с задержкой около секунды**: замер трафика читает их после паузы 1,5 с. Без паузы в пробе недосчитывался трафик докачки.
- **Размер части скачивания зависит от файла**: для 8 МиБ это 64 КиБ (E4: 256 КиБ для документа 512 МиБ). Допуск «сразу за запросом» в прототипе поставлен в 256 КиБ.
- **Асинхронное скачивание, которое оборвалось, не сообщает ошибки**: единственный признак — апдейт `is_downloading_active = false` при непокрытом окне или отсутствие прогресса. Прототип проверяет оба признака и повторяет `downloadFile`.
- **Проба пункта 7 в `probe/e10_p7.csv`** снята до правки паузы счётчиков: трафик докачки там занижен (0,0 КиБ). Окончательные данные — в основных CSV.
