# 10. E2E на живом Telegram, режим бота

Первый запуск настоящего `telega-fs` с `store = "telegram"` по плану E2E-тестов на боевых серверах (нагрузку несёт бот, аккаунт пользователя только создаёт и удаляет канал, ни одного сообщения с него). Скрипт — `tests/e2e/e2e_basic.sh` (запускается вручную, CMake: `-DTELEGA_FS_E2E=ON`, тест `telega_fs.e2e_basic` с меткой `e2e`), настройка и уборка канала — `tgfs-bench e2e setup | inspect | teardown`. Секреты и id в отчёт не попадают.

## Итог

**Сценарий прошёл: sha256 файла 200 МиБ на «машине B» (пустые каталоги, пустой кэш) совпал с исходным, дерево целиком (sha256 всех файлов, режимы, размеры, каталоги) совпало на A после перемонтирования, на B и на A после `logout` и `login`.** Для этого пришлось исправить две ошибки (ниже); пауза около минуты при монтировании сразу после `init` остаётся (кэш TDLib).

## Время

Один полный прогон (последний, после исправлений), одна «машина» на этапе, сеть домашняя. Это один прогон, а не серия из пяти повторов, которую требуют правила сетевых замеров, поэтому цифры ориентировочные.

| Этап | Время |
|---|---|
| Монтирование A сразу после `init` | 60,7 с (кэш TDLib, см. ниже) |
| Запись 200 МиБ и мелких файлов в точку монтирования (overlay) | 2,9 с |
| Первый `fsync` большого файла: заливка всех данных и коммит | 152,5 с (200 МиБ + мелочь, 33 документа .bin/.idx всего за прогон; около 1,4 МиБ/с, упор в `send_rate` = 12 действий в минуту: чанки ушли по одному, 25 штук. Первая версия заметки объясняла это размером 8 МиБ + 2088 байт, но порог альбома этот размер учитывает. Настоящая причина: у Vfs всего `upload_concurrency` = 2 потока загрузки, каждый ждёт в `put_chunk` свой документ, и попутчиков для альбома не набирается. Исправление — больше одновременных `put_chunk`, принято, см. «Что приняли по итогам») |
| Второй `fsync` (малый файл) / `fsyncdir` | 30,0 с / 15,0 с (два и один коммит по 3 действия, 15 с на коммит при 12 действиях в минуту) |
| Размонтирование (`fusermount3 -u`, нечего заливать) | 1,0 с |
| Размонтирование по `SIGTERM` (запись без `fsync`, два коммита) | 9,1 с |
| Монтирование на B (пустые каталоги, `master_key` из головы) | 1,8 с |
| Холодное чтение файла 200 МиБ на B | 186,1 с (1,1 МиБ/с, см. ниже) |

Сообщений в канале по итогам: 40 документов (33 `.bin` — чанки и пакеты, 7 `.idx` — снимок и дельты поколений 1–7) и 8 служебных (создание канала и 7 закреплений). Всего 48 серверных id.

Холодное чтение 1,1 МиБ/с против 8–11 МиБ/с в E7: это не ошибка, а отсутствие readahead (веха M3). `sha256sum` читает файл по 128 КиБ, и `ChunkReader` на каждое чтение делает отдельный `downloadFile` диапазона (около 0,1 с на запрос).

## Найденные ошибки

### 1. Монтирование сразу после `init` (или размонтирования) отвечало «нет головы»

Через 1 с после успешного `init` (закрепление голова-снимка прошло, `getChatPinnedMessage` в процессе `init` его видел) команда `mount` в новом процессе падала: `the channel has no file system head`. Повторные попытки через 30 и 50 с давали то же, через 67 с голова появилась (в полном прогоне окно ожидания закончилось на 61-й секунде).

Причина: прежнее описание платформы говорило, что «после старта процесса голова читается с сервера». Это верно для пустой БД TDLib (E2). У профиля БД TDLib остаётся на диске, в ней лежит закэшированный `ChannelFull` («закреплённых нет», снятый при `init`), и `getChatPinnedMessage` отдаёт его до 60 с. После размонтирования такого не наблюдалось: повторное монтирование A заняло 0,6 с (кэш того же процесса видел свой pin до закрытия). Ветка «голова старее локальной» покрыта только тестом на фейке.

Исправление: `mount_fs` повторяет чтение головы раз в `stale_head_period` (10 с), но не дольше `stale_head_window` (90 с), если локально известна голова H (есть индекс и `base_generation > 0`), а канал отдал «нет головы» или голову с `msg_id < H`. Приложение включает окно только для `store = "telegram"` (значения те же, что у повтора CAS, `cas_retry_window` и `cas_retry_period`). На новой машине (нет локального индекса) ждать нечего, и пустая БД читает голову с сервера сразу (B: 1,8 с).

Файлы: `src/meta/mount.cpp` (`read_head_for_mount`), `src/meta/mount.h` (`MountOptions::stale_head_window`, `stale_head_period`), `src/app/commands.cpp`. Тесты: `tests/unit/commit/mount_test.cpp`, `Mount.StaleEmptyHeadIsRetriedWhenTheLocalHeadIsKnown`, `Mount.StaleOlderHeadIsRetriedWhenTheLocalHeadIsKnown`, `Mount.StaleHeadThatNeverClearsFailsAfterTheWindow`, `Mount.StaleHeadIsNotRetriedWithoutAWindowOrALocalHead`.

Остаётся: монтирование A сразу после `init` ждёт около минуты (в логе строка «checking again in 10 s»). Принудительное обновление кэша не найдено (в E2 `getSupergroupFullInfo` не помогал). Если окно (90 с) кончилось, а голова не видна, монтирование отказывает как раньше.

### 2. Чтение чанка: `downloadFile: 200: Canceled by another downloadFile request` и `EIO`

После перемонтирования на A чтение `big.bin` и ещё пяти файлов (крупные и пакеты) давало `EIO`. В логе: `read of chunk N failed: ... downloadFile: 200: Canceled by another downloadFile request`, по нескольку раз для одного чанка.

Причина: TDLib отменяет прежний `downloadFile` файла, когда приходит новый запрос на тот же `file_id` (с другим диапазоном). Пользовательское чтение и readahead одного чанка шли параллельно (до `download_concurrency` = 4 запросов на файл), отменяли друг друга, и обе попытки `read_range` (с обновлением file_id) заканчивались ошибкой 200 (она у нас `permanent`).

Исправление: запросы `downloadFile` по одному файлу в `TelegramStore` идут по очереди (`FileGuard`: набор занятых `file_id`, ожидание до `read_timeout`), по разным файлам параллельно в пределах `download_concurrency`. Затрагивает `download_and_read` (чтение диапазона и голова) и `read_index`.

Файлы: `src/store/telegram_store.cpp`. Тест: `tests/unit/store/telegram_store_test.cpp`, `ReadTest.ReadsOfTheSameFileDoNotCancelEachOther` (в `fake_telegram.h` добавлен `set_cancel_overlapping_downloads`: новый запрос на файл отменяет старый ответом 200; без исправления тест падает). Тест `ReadTest.DownloadConcurrencyIsBounded` теперь читает разные файлы: параллелизм по одному файлу невозможен по построению.

## Что приняли по итогам

1. **Голова после перезапуска.** Утверждение «после старта процесса голова читается с сервера» верно только для пустой БД TDLib. Кэш `ChannelFull` лежит в БД и переживает перезапуск, поэтому голова может не показываться до минуты после `init` или размонтирования. Принято: если локально известна голова новее той, что отдал канал, чтение повторяется раз в 10 с, но не дольше 90 с (только для Telegram).
2. **Скачивания одного файла.** Запросы `downloadFile` по одному файлу не выполняются параллельно: TDLib отменяет прежний запрос ответом `200 Canceled by another downloadFile request`. Параллелизм достигается только между файлами, а readahead ставится в очередь по тому же файлу, а не идёт рядом.
3. **Заливка с Vfs.** Чтобы `TelegramStore` набирал попутчиков для альбома, Vfs держит больше одновременных `put_chunk`, чем `upload_concurrency`: до `min(10 · upload_concurrency, 32)` (по умолчанию 20), если Store собирает альбомы.
4. **E2E на боевых серверах.** Сценарий идёт на боевых серверах Telegram, ботом; скрипт и опция `TELEGA_FS_E2E` описаны в шапке `tests/e2e/e2e_basic.sh`.
5. **Наблюдение, без решения.** `fsync` малого файла сделал 2 коммита (30 с: поколение 3 — снимок из-за `checkpoint_ratio`, дельта первого коммита 27 КиБ больше 25 % снимка 1,4 КиБ; поколение 4 — дельта 483 байта), `fsyncdir` — один (15 с). Почему один `fsync` дал два коммита, я не выяснял (возможно, `sync FILE` вызывает и `flush`, и `fsync`); цена — 3 лишних действия.

## Не проверено

- Прогон в режиме пользователя и переключение профиля между режимами (только с отдельным аккаунтом).
- Ветка повтора CAS из-за кэша TDLib при коммите (в этом прогоне не сработала).
- Сбои сети посреди заливки и `sync_timeout` (на живом Telegram).
- `FLOOD_WAIT` (ни одного не было, ожидание лимитера на 429 не проверялось).
- Команды `status`, `sync`, `fsck`, `gc`, `recover` (не реализованы).

## Как повторить

```
cmake --preset dev -B build/w-e2e -DTELEGA_FS_BUILD_TOOLS=ON -DTELEGA_FS_E2E=ON
cmake --build build/w-e2e -j4 --target telega-fs tgfs-bench
tests/e2e/e2e_basic.sh                    # напрямую, около 15 минут
TELEGA_FS_E2E_RUN=1 ctest --test-dir build/w-e2e -L e2e --output-on-failure   # через ctest
```

Нужны `cred.secret` в корне репозитория (`api-id`, `api-hash`, `bot-token`) и вход пользователя бенча (сессия `user` в state-dir бенча по умолчанию). Без `TELEGA_FS_E2E_RUN=1` ctest пропускает тест (код 77), поэтому `ctest -LE long` в сеть не ходит.
