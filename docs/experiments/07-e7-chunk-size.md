# E7. Размер чанка

Эксперимент E7 из раздела 17.10 спеки (веха M2, боевые серверы Telegram, только режим бота). Инструмент: `tgfs-bench e7 ...` (`tools/bench/tdbench/cmd_e7.cpp`, отправка `send_load.*`, общий код `run_common.*`, `exp_common.*`, шифрование чанков `src/crypto/chunk.*`), набор C3 (`tools/bench/corpora/README.md`, `c3-sizes.csv`), сырые данные: `docs/experiments/07-e7-chunk-size/*.csv` (пробные прогоны — в `probe/`).

## Метод

Один фоновый процесс (`<state-dir>/tgfs-bench-e7 e7 run`, возобновляемый, flock на сессию, SIGTERM сохраняет состояние). Серия — размер чанка S (8, 16, 32, 64 МиБ) и номер повтора; 5 кругов по 4 размера, чтобы время суток не смещало один размер; пауза между сериями 300 с после удаления. Серия «чистая», если ни одна фаза не возобновлялась после обрыва, нет сетевых ошибок и таймаутов и нет расхождений при сверке; для нечистой серии добавлялся бы повтор (до 3 лишних на размер). Лишних повторов не понадобилось.

Набор 2 ГиБ — часть C3 (`tools/bench/corpora/README.md`): файл 1 ГиБ (он же файл для RMW) и первые по порядку 171 файл 1–10 МиБ суммой 1017,8 МиБ (сумма всех 500 файлов 2738,6 МиБ). Файлы 2 и 4 ГиБ из C3 не заливались: для выбора S они ничего не добавляют (скорость определяют лимиты), а стоят 9 и 18 минут заливки на лимите по байтам на каждый размер и повтор.

Фазы серии:

1. **`upload_big`** — файл 1 ГиБ настоящими зашифрованными чанками (формат раздела 5, `encrypt_chunk_file`). Чистая проверка формулы: все чанки одного размера.
2. **`upload_small`** — 171 файл 1–10 МиБ (файл > S режется на чанки: при S = 8 файл 8–10 МиБ даёт чанк 8 МиБ и остаток).
3. **`dl_big`, `dl_small`** — скачивание тех же документов: `getMessages` пачками по 100 (пауза 10 с) → `deleteFile` → проверка, что локального файла нет на диске → `downloadFile(offset 0, limit 0, synchronous)` с `download_concurrency` = 4 → расшифровка и сверка с данными по seed вне замера. Холодный кэш подтверждён для 4850 из 4850 скачиваний.
4. **`rmw`** — 100 перезаписей по 4 КиБ в случайных местах файла 1 ГиБ, подряд, как по 8.1: `getMessages` по `msg_id` → `deleteFile` → скачать чанк целиком → расшифровать → записать 4 КиБ → зашифровать заново (новый `chunk_id` и nonce) → залить. Время — от начала до `updateMessageSendSucceeded`; отдельно записано ожидание бакетов, чтобы получить время без него. После каждой перезаписи чанк сверяется с ожидаемым (данные по seed плюс все прежние правки): 500 из 500 на размер совпали.
5. **`cleanup`** — удаление всех документов серии (включая старые версии чанков после RMW) пачками по 100.

Отправка по разделу 10.2: два token bucket (`send_rate` 12 с всплеском 5, `send_bytes_rate` 224 МиБ/мин, ёмкость байтового бакета 96 МиБ), `upload_concurrency` = 2, документы не больше `album_max_doc_size` (8 МиБ) — альбомы по 10 из подряд идущих документов очереди (альбом = 2 действия, байты — сумма документов), остальные по одному; `FLOOD_WAIT` останавливает все отправки на указанное время плюс джиттер до 10 %, повторы по правилам раздела (не понадобились ни разу). Бакеты на старте каждой фазы пустые: всплеск не завышает скорость.

Размер для альбомов считается по **открытому тексту чанка**: файл чанка 8 МиБ равен 8 МиБ + 2088 байт (заголовок 40 байт и 16 байт на сегмент по 64 КиБ) и формально больше 8 МиБ. Сообщения о правке спеки — в разделе «Выводы».

Скорость заливки в CSV и таблицах — открытый текст в МиБ за **полное время фазы** с первой отправки (`mib_s`) и «установившаяся» от завершения первого задания до последнего (`steady_mib_s`, как в E5 первый цикл исключается). Решение считается по полному времени.

Разброс между повторами 0,3 % и меньше: скорость целиком задана лимитами, а не каналом (сам канал при заливке по одному документу выше, 12–20 МиБ/с, E5). Ни одного `FLOOD_WAIT` и ни одного повтора за 6850 документов.

**Файл 1 ГиБ.** Ожидание E5 подтверждено: 16 МиБ упирается в `send_rate` (12 × 16 МиБ = 192 МиБ/мин = 3,2 МиБ/с), 32 и 64 МиБ — в `send_bytes_rate` (3,73 МиБ/с), и 8 МиБ тоже: альбомы по 10 стоят 2 действия, то есть 0,2 действия на документ, и `send_rate` до 8 × 12 / 0,2 = 480 МиБ/мин не мешает, лимит байтовый.

**Мелкие файлы.** Состав: 171 файл, из них 46 крупнее 8 МиБ. При S ≥ 16 файл 8–10 МиБ — один чанк крупнее 8 МиБ, эти 46 документов идут по одному и разрывают цепочки альбомов: 29 альбомов (121 документ) и 50 одиночных документов — 108 действий, то есть 540 с на `send_rate` = 12 в минуту при 272,7 с по байтам. Ровно 1,88 МиБ/с (1017,8 МиБ за 541 с). При S = 8 файл 8–10 МиБ даёт чанк 8 МиБ и остаток, все 217 документов не больше 8 МиБ, 22 альбома — 44 действия, лимит по байтам (3,71 МиБ/с).

**Использование действий.** За заливку набора: 70 действий (S = 8), 172 (16), 140 (32), 124 (64). При S = 8 `send_rate` занят на 47 % (заливка идёт на лимите байтов), а при S = 16 на 100 % и целиком: на коммиты (3 действия) ничего не остаётся. Это важно для реальной ФС (раздел «Выводы»).

### Критерий решения 17.10

Скорость заливки относительно максимума среди проверенных размеров (медианы):

| S, МиБ | Весь набор 2 ГиБ | Один файл 1 ГиБ | Весь набор, оценка с пакетами (`pack_threshold` = 4 МиБ), без реорганизации очереди | То же, альбомы собираются из любых подходящих документов |
|---|---|---|---|---|
| 8 | 3,688 (**100 %**) | 3,675 (99,1 %) | 3,73 (**100 %**) | 3,73 (**100 %**) |
| 16 | 2,367 (64,2 %) | 3,186 (85,9 %) | 2,40 (64 %) | 3,05 (82 %) |
| 32 | 2,498 (67,7 %) | 3,709 (**100 %**) | 2,54 (68 %) | 3,27 (88 %) |
| 64 | 2,493 (67,6 %) | 3,689 (99,5 %) | 2,54 (68 %) | 3,27 (88 %) |

Последние два столбца — расчёт, не измерение (раздел «Оценка с пакетами»). Какой бы столбец ни брать, 8 МиБ — наименьший из проверенных и подходит под критерий (он сам и есть максимум в первом столбце, 99 % во втором); у него же самый дешёвый RMW. Проходят критерий и другие размеры только в столбцах «один файл» и «альбомы из любых документов»; тогда правило «наименьший размер, при нескольких — с более дешёвым RMW» тоже даёт 8 МиБ.

Размеры меньше 8 МиБ не проверялись. По тому же расчёту 4 МиБ дают на лимите байтов 56 документов в минуту, то есть 5,6 альбома и 11,2 действия в минуту, то есть уже на границе `send_rate` = 12 даже без коммитов, а 2 МиБ ограничивался бы `send_rate` (около 2 МиБ/с); 8 МиБ (28 документов, 2,8 альбома, 5,6 действия в минуту из 12) близок к оптимуму.

|---|---|---|---|---|
| 8 | 14,19 (11,89–14,81) | 8,74 (8,55–8,81) | 9,04 (8,60–9,21) | 0,73 с |
| 16 | 12,09 (10,73–14,41) | 8,16 (6,89–9,16) | 9,11 (8,73–9,20) | 1,17 с |
| 32 | 11,57 (11,14–12,58) | 8,46 (7,82–8,93) | 9,13 (8,96–9,21) | 2,07 с |

Размер чанка на скорость заметно не влияет: разброс между повторами у одного размера (до 20 %) сравним с разницей между размерами. Время одного чанка после старта хорошо ложится на `0,28 с + S / 17,9 МиБ/с` (8 МиБ: 0,73 с; 64 МиБ: 3,85 с): запрос стоит около 0,28 с, поэтому с ростом чанка скорость растёт немного (11,5 МиБ/с при 8 МиБ, 16,6 при 64). Мелкие файлы идут медленнее большого (на запрос приходится по 0,28 с, а документ около 6 МиБ). Для S = 16, 32 и 64 набор мелких документов один и тот же, но при 64 МиБ он скачивался заметно медленнее (6,0 МиБ/с против 8,2–8,5 в каждом из 5 повторов); причину не выяснял.

**TDLib при `downloadFile` с одинаковым приоритетом исполняет запросы по одному, самый новый первым.** Видно по `e7_downloads.csv`: при `download_concurrency` = 4 запросы 0–3 стартуют вместе (S = 64, `s64-r3`: 4 запроса), запрос 3 завершается за 14 с, затем каждый следующий запрос стартует сразу после предыдущего и идёт 3,7–4,8 с (около 17 МиБ/с, скорость одного потока), а запросы 0, 1 и 2 завершаются на 65-й, 69-й и 72-й секундах, уже когда новее них ничего не осталось, с интервалом 3,5 с (тоже последовательно). Итог: четыре параллельных запроса дают скорость одного, а самые старые запросы ждут (в `dl_big` первые четыре чанка: медиана 10,7 с при S = 8 и 57 с при S = 64 против 0,73 и 3,85 с у остальных). В `dl_small` первые четыре запроса в 74 случаях из 80 (20 серий × 4) завершались ошибкой `400: File download has failed or was canceled` (в `dl_big` 5 раз), и следующая попытка после `getMessages` проходила за обычное время (0,7–3,5 с). Причину отмены я не установил (в `dl_big` те же ожидания по 60–75 с отменой не заканчивались); все 4850 скачиваний завершились успешно, 79 из них со вторым или третьим разом, 0 несовпадений данных.

Следствие для спеки: у чтения должен быть приоритет. Запрос чтения под пользователем нельзя ставить в одну очередь с упреждающим чтением (readahead) на равных: новое упреждающее чтение обгоняет старый запрос, который ждёт пользователь. Приоритет `downloadFile` (1–32) в E7 не менялся и не проверялся (это следует проверить в M3), что он управляет этим порядком, — вывод по порядку ответов, а не измерение.

- Перезапись одного чанка при S = 8 тратит 8 МиБ из 224 МиБ/мин лимита по байтам, при 64 МиБ — 64 МиБ. Случайная запись в большой файл (например, базу данных) на 64 МиБ даёт 3,5 перезаписи в минуту, на 8 и 16 МиБ — 12, и на 8 МиБ при этом остаётся 57 % бюджета байтов на остальную заливку.
- Трафик на одну перезапись: примерно 2 × S (чанк вниз и вверх): 16, 32, 64 и 128 МиБ. За 100 перезаписей: 0,8, 1,6, 3,2 и 6,4 ГиБ в каждую сторону.
- `getMessages` по одному id занимает 0–1 мс (сообщение известно сеансу), `FLOOD_WAIT` на 100 × 20 одиночных запросов `getMessages` не было, и в RMW он не появлялся (0 из 2000).
- Все 2000 перезаписей прошли с первой попытки (0 `FLOOD_WAIT`, 0 повторов), сверка чанка до правки с ожиданием — 2000 из 2000.

### Оценка с пакетами и `pack_threshold` = 4 МиБ

В реальной ФС файлы до `pack_threshold` = 4 МиБ (E9) уходят в пакеты, а позиционными чанками остаются файлы больше 4 МиБ. В E7 мелкие файлы заливались как отдельные чанки, поэтому ниже пересчёт на тех же размерах файлов (скрипты `model_packs_c3.py` и `model_packs_c2.py` в каталоге данных). Модель: время заливки = max(действия / 12 в минуту; байты / 224 МиБ в минуту) для той же последовательности документов с теми же правилами альбомов. Проверка модели по измеренному: время мелких файлов без пакетов 273 и 540 с против измеренных 275 и 541 с, файл 1 ГиБ 274 и 320 с против 279 и 321 с (расхождение до 1,6 % за счёт разогрева).

В наборе мелких файлов (171 файл, 1017,8 МиБ) в пакеты уходят 48 файлов до 4 МиБ (124,3 МиБ), позиционными остаются 123 файла (893,5 МиБ), из них 46 крупнее 8 МиБ. Файлы в пакет добавляются подряд, пока не превысят `pack_target` (S = 8: пакет 8 МиБ, S = 16: пакет 16 МиБ, как у E9):

| S, МиБ | `pack_target`, МиБ | Документов (набор 2 ГиБ) | Действий в мелких | Мелкие, МиБ/с | Весь набор, МиБ/с | То же, если альбомы собираются из любых подходящих документов |
|---|---|---|---|---|---|---|
| 8 | 8 | 315 | 38 | 3,73 | **3,73** | 3,73 |
| 16 | 16 | 196 | 106 | 1,92 | **2,40** | 3,05 |
| 16 | 8 | 205 | 103 | 1,98 | 2,45 | 3,14 |
| 32 | 16 | 164 | 106 | 1,92 | 2,54 | 3,27 |
| 64 | 16 | 148 | 106 | 1,92 | 2,54 | 3,27 |

- Пакеты 16 МиБ уходят по одному и больше не помогают альбомам, так что картина при S ≥ 16 почти та же, что без пакетов: файлы 4–8 МиБ идут в альбомы, файлы 8–10 МиБ и пакеты 16 МиБ по одному. Пакеты улучшают только число документов (на 17 % меньше при S = 16, на 9 % при S = 8).
- Если очередь отправки собирает альбомы из любых подходящих документов, а не из подряд идущих (при S ≥ 16 действий 70 вместо 106), S = 16 даёт 3,05 МиБ/с = 82 % от 3,73: на границе критерия. Реальный `TelegramStore` стоит строить именно так, но запас у S = 16 минимальный и любой коммит (3 действия, раздел 10.2) снимает его.
- **Копия «Домашнего каталога» C2** (65 ГиБ, 659 тыс. файлов; грубая оценка: файлы до 4 МиБ в пакеты по 85 % заполнения, остальные чанками, альбомы из любых документов): время заливки 4,9 ч при S = 8 (упор в байты), 6,1 ч при 16 МиБ (упор в `send_rate`: 4410 действий), 4,9 ч при 32 МиБ и 4,9 ч при 64 МиБ. С коммитами раз в 60 с (3 действия, 25 % `send_rate`): 4,9 ч (S = 8), 8,2 ч (16 МиБ), 6,1 ч (32 МиБ), 5,2 ч (64 МиБ). 8 МиБ лучший из четырёх, потому что у него вдвое меньше действий на ГиБ.

## Выводы

1. **`chunk_size` = 8 МиБ.** Решение по критерию 17.10 (наименьший размер с эффективной заливкой ≥ 80 % от максимума, при нескольких — с дешёвым RMW). В пользу, помимо критерия: наименьшая нагрузка на `send_rate` (47 % против 100 % у 16 МиБ при заливке), самый дешёвый RMW (1,9 с против 2,5–7,7 с), вдвое меньше трафика на перезапись, скорость заливки не зависит от состава набора, а у 16–64 МиБ падает до 1,9–2,5 МиБ/с на файлах 1–10 МиБ. Против: на 47 % больше сообщений на ГиБ (173 против 118), больше строк индекса и больше пачек удаления; скорость скачивания на один чанк чуть ниже (11,5 МиБ/с против 16,6 при 64 МиБ из-за 0,28 с на запрос), но на набор целиком разницы не видно.
2. **Неизмерено.** Размеры меньше 8 МиБ (по расчёту 4 МиБ на границе `send_rate`), режим пользователя (у него лимиты не измерены), параллельность скачивания больше одного потока (получилась последовательной, см. выше), приоритеты `downloadFile`, файлы 2 и 4 ГиБ, причина отмены первых четырёх скачиваний в `dl_small` и низкая скорость `dl_small` при 64 МиБ.
3. **Альбомы по 8 МиБ** ходят устойчиво: 35 альбомов и 345 документов за серию, 20 серий, 0 `FLOOD_WAIT` и 0 частичных доставок на лимите 224 МиБ/мин (E6 проверял 1 и 16 МиБ, порог 8 МиБ был расчётным; теперь он измерен для 8 МиБ).

## Грабли TDLib и инструмента

- `downloadFile` с `limit` = 0 и `synchronous` = true для 64 МиБ возвращается только после полной загрузки; одновременно идущие запросы одного приоритета выполняются по одному, новейший первым (выше). `deleteFile` после отправки документа этим же сеансом не сбрасывает его поле `local` (TDLib помнит путь исходника): холодность проверялась по отсутствию файла на диске. Холодность и объём скачанного подтверждены счётчиком трафика (1026,6 МиБ принято на 1024 МиБ данных).
- Ошибка `400: File download has failed or was canceled` на ожидающем скачивании (первые 4 запроса `dl_small`).
- `getNetworkStatistics(only_current = true)` в TDLib 1.8.70 даёт суммарные отправленные и принятые байты процесса, по разности двух вызовов считается трафик фазы.
- Время RMW зависит от того, засчитывать ли ожидание бакетов: поэтому в CSV оба значения.
- Файл чанка 8 МиБ равен 8 МиБ + 2088 байт, в альбомы он попадает только при проверке порога по открытому тексту.
- Метка `steady_mib_s` для скачивания совпадает с `mib_s` (в окне нет «первого задания»), поэтому разницу между ними смотреть только для заливки.
