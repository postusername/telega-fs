# E8. Инлайн-файлы

Эксперимент E8 из раздела 17.11 спеки (веха M2), **целиком офлайн**: Telegram не участвует, в сеть никто не ходил. Инструменты: `tools/bench/e8/` (`tgfs-e8`, `run-e8.sh`, `analyze-e8.py`) и `tools/bench/sim/` (`tgfs-sim`); наборы: `tools/bench/corpora/`; сырые данные: `docs/experiments/08-e8-inline/*.csv`.

**Что замер, а что расчёт.** Размеры снимков и дельт, время локальной сборки снимка и время распаковки блоба при монтировании — **замеры** на настоящем telega-fs (`VACUUM INTO`, zstd 9 и 3, шифрование, `LocalDirStore`). Число сообщений — **результат модели** `tgfs-sim` (E9). Время заливки снимка и «стоимость коммита» — **расчёт** по лимитам E5 и разделу 10.2 (14 МиБ/с на поток, бакет 224 МиБ в минуту), а не замер в Telegram.

## Метод

### Наборы

Все четыре набора строятся тем же кодом, что C4 в E1 (`corpora/c4_gen.cpp`, вставка через `index_ops`: Vfs и FUSE не нужны, данные файлов не создаются). Каталоги по 50 записей. Для E8 генератор получил режим «размеры заданы»: размер каждого файла берётся из списка, а **класс хранения выводится из порогов индекса при запечатывании** (SPEC 6.5), а не из фиксированных долей:

- размер 0 — файл без данных (как в Vfs: ни инлайна, ни экстентов);
- `size ≤ inline_max` и `inline_bytes + size ≤ inline_budget` — инлайн, содержимое пишется `set_inline` (бюджет проверяет тот же код, что в продукте). Не влезший файл идёт в пакет, уже лежащие не выселяются. Файлы создаются по порядку списка, поэтому при нехватке бюджета инлайн получают первые по порядку;
- `size ≤ pack_threshold` (4 МиБ, E9) — пакет `kind = 2` (один экстент `idx = 0` с `chunk_off`, пакеты закрываются по `pack_target` 16 МиБ);
- иначе позиционные чанки по `chunk_size` 16 МиБ.

**Модель размеров C4 для E8.** SPEC 17.3 даёт 90 % пакетов, 5 % инлайн и 5 % позиционных при `inline_max` 4 КиБ, а инлайн-файлы берёт размером 16–600 байт: это не распределение размеров, а готовые доли, и при другом `inline_max` они не пересчитываются. Здесь так: 5 % файлов — позиционные (логарифмически равномерно от 4 МиБ + 1 до 128 МиБ), остальные 95 % — логарифмически равномерно от 16 Б до 4 МиБ. Доля файлов не больше 1 / 2 / 4 / 8 / 16 КиБ получается 31,7 / 37,0 / 42,3 / 47,6 / 52,8 % (C1: 14,1 / 38,4 / 62,4 / 78,7 / 88,2 %, C2: 31,8 / 44,3 / 55,5 / 69,7 / 80,7 %), средний размер файла до 4 КиБ — 735 байт (C1 1859, C2 1175). Это грубее настоящих распределений, но на C4 с миллионом файлов бюджеты 16 и 64 МиБ заполняются при любом `inline_max` от 1 КиБ, то есть можно мерить именно **заполненный бюджет**, как требует критерий. На C4 при 100 000 inode бюджет 64 МиБ заполняется не всегда (колонка «бюджет полон»).

Параметры ФС: `chunk_size` 16 МиБ, `pack_threshold` 4 МиБ, `pack_target` 16 МиБ (E9), `inline_max` 0, 1, 2, 4, 8 и 16 КиБ × `inline_budget` 4, 16 и 64 МиБ (для `inline_max` = 0 бюджет ни на что не влияет, одна комбинация).

### Что меряется на каждой комбинации (`tgfs-e8 index`)

На настоящей ФС (`init_fs`, `mount_fs`, `LocalDirStore`, `CommitManager`) после сборки индекса:

1. **Снимок, 3 повтора на одном и том же состоянии:** `commit(true)` — `VACUUM INTO`, zstd 9, шифрование. Метрики `CommitMetrics`: размер файла индекса, после zstd, блоб, время по стадиям. Затем блоб читается из канала и распаковывается так, как это делает монтирование (`open_chain_blob`: расшифровка, zstd, BLAKE2b) — время распаковки при монтировании.
2. **Дельты после снимков, 3 повтора:** правка 1, 100 и 1000 инлайн-файлов (новое содержимое той же длины, `mtime` и `ctime`; выбор без повторов из файлов, ставших инлайн; нагрузка 4 из E1). Настоящий `commit(false)` по дельта-журналу: размер патча, после zstd 3, блоб. Для размеров патча вариант «100 файлов» — типичная дельта критерия (как в E1).

Цепочка при расчёте стоимости: `max_chain` = 16 и `checkpoint_ratio` = 0,25 (E1). Цепочка закрывается снимком, когда сумма дельт превысит 0,25 размера снимка, поэтому на маленьком индексе она короче (C1: 2–3 дельты вместо 16, см. «Критерий решения»).

### Расчёт времени заливки и стоимости коммита (расчёт, не замер)

- Заливка блоба `B` одним документом: `B / 14 МиБ/с` (E5: 13,6 МиБ/с при одном потоке, модель `tgfs-sim`). Постоянные части коммита (CAS 0,3 с, задержка документа 0,2 с, pin и unpin по 0,3 с, всего 1,1 с) от инлайна не зависят и в колонку «заливка» не входят.
- Бакет байтов 224 МиБ/мин (3,73 МиБ/с): блоб `B` занимает его на `B / 3,73 МиБ/с`. Это то, на сколько блоб задержит чанки при насыщенной очереди (E5, E7); колонка «при занятом бакете» — более жёсткая оценка.
- Стоимость коммита: `(S + k · d) / (k + 1)`, где `S` — локальная сборка снимка плюс заливка, `d` — то же для типичной дельты, `k = min(16, ⌊0,25 · S_блоб / d_блоб⌋ + 1)`. «Локальная сборка» — медиана по повторам (`VACUUM INTO` + zstd + шифрование), для дельты — забор под блокировкой + zstd + шифрование.
- Критерий: `≤ 0,1 · commit_interval = 6 с`.

### Сообщения (`tgfs-sim`, `run-e8.sh`)

Модель E9 с итогами E9: `pack_threshold` 4 МиБ, `pack_target` 16 МиБ, `pack_max_age` 30 с, лимиты включены, `commit_interval` 60 с. В симулятор добавлена опция `--commit-defer 5`: отсрочка коммита по таймеру, пока очередь заливки не пуста (SPEC 7.1, не дольше 5 · `commit_interval`); по умолчанию 0, поэтому прогоны E9 воспроизводятся без изменений (проверено на `e9_sim_c1_inline_16MiB.csv`: совпадает побайтно). Нагрузки: C1 (распаковка, переключение между десятью коммитами с паузой 60 с, то же в обратном порядке, переключение с `fsync` после 2 % файлов), C2 (распаковка), C4 (распаковка; для симулятора берутся только файлы до `pack_threshold`, позиционные от инлайна не зависят, размеры те же, что в индексе). «Сообщения» — документы (чанки, пакеты, блобы индекса), медиана по seed. Модель блобов индекса в симуляторе грубая, поэтому размеры блобов берутся из `tgfs-e8`, а не из симулятора.

### Размер и стоимость снимка

Колонки: «инлайн» — сколько файлов и МиБ реально легло в индекс; «бюджет полон» — `inline_bytes ≥ 0,97 · inline_budget`; «снимок» — блоб в канале (zstd 9 и шифрование), одно значение на три повтора (между повторами размер различается не больше чем на 0,01 МиБ); «локальная сборка» — `VACUUM INTO` + zstd + шифрование, секунды, медиана [минимум..максимум] по 3 повторам; «заливка» и обе «стоимости коммита» — **расчёт**, секунды; «скачать+распаковать» — **расчёт** скачивания при 20 МБ/с плюс замеренная распаковка (для монтирования).

### Критерий решения (расчёт)

Колонки «коммит в среднем» в таблицах выше. Худшие значения по всем 64 комбинациям:

| Вариант расчёта | Худшая средняя стоимость коммита | Порог |
|---|---|---|
| заливка 14 МиБ/с, только то, что зависит от индекса | 1,01 с (C4 1M, 2 КиБ/64 МиБ; 1,00 с при 8 и 16 КиБ) | 6 с |
| то же, но блоб занимает байтовый бакет (насыщенная очередь) | 2,30 с (C4 1M, 16 КиБ/64 МиБ) | 6 с |
| бакет плюс постоянная часть коммита 1,1 с | 3,4 с | 6 с |

Все 64 комбинации (4 набора × 16) проходят по всем трём вариантам. Для заполненного бюджета там, где набор его не заполнил (C4 100k с 64 МиБ: от 7,1 до 58 МиБ инлайна при порогах 1–8 КиБ, C1 всегда), `analyze-e8.py` дополнительно оценивает снимок при заполнении (`snap_full_est_mib`, `avg_commit_full_*` в `e8_summary.csv`): и по ним все проходят; оценка линейная и честна только там, где файлов хватило бы на заполнение. Самый тяжёлый случай (C4 1M, 64 МиБ, случайные данные): снимок 110 МиБ, заливка 7,9 с каждые 17 коммитов.

Критерий слабый: отсечь он мог бы только бюджет в сотни мегабайт (стоимость коммита дошла бы до 6 с при снимке около 1,4 ГиБ: 6 с · 17 коммитов · 14 МиБ/с), а сетка E8 до 64 МиБ.

Цепочка на маленьком индексе: на C1 с инлайном дельта 44–78 КиБ при снимке 0,4–0,9 МиБ, поэтому `checkpoint_ratio` закрывает цепочку после 2–3 дельт. Средняя стоимость коммита при этом 0,02–0,05 с: на выбор не влияет, пересматривать `checkpoint_ratio` по итогам E8 незачем.

### Другие выгоды инлайна

- **Холодное чтение без сети.** Инлайн-файл читается из индекса без сети и без кэша (SPEC 6.5). По E9 холодное чтение мелкого файла из пакета стоит около 120 мс (2–64 КиБ), то есть при 4 КиБ и 16 МиБ без сети читаются 14 380 файлов C2 (4 % файлов не больше 4 КиБ; пакеты останутся для остальных 342 000), 1066 файлов C1 (полное холодное чтение этих файлов по одному заняло бы около 130 с) и по 22 987 файлов на C4 (100k и 1M). Это оценка по E9, в этом эксперименте сеть не мерилась. Выигрыш на мегабайт бюджета выше у малых порогов: C2 при 16 МиБ — 42 262 файла при 1 КиБ, 14 380 при 4 КиБ, 4816 при 16 КиБ. Но инлайн получают первые по порядку запечатывания файлы, а не самые читаемые, поэтому на заполненном бюджете выигрыш случаен.
- **Меньше `fsync`-пакетов** — единственное, где экономия сообщений настоящая (см. выше).
- **Мёртвое место в пакетах** инлайн почти не убирает. C1 с переключениями: мёртвых байт в залитых пакетах 95,7 МиБ без инлайна, 95,0 МиБ при 4 КиБ и 92,3 МиБ при 16 КиБ (всего в пакетах 116,7, 114,2 и 108,2 МиБ; доля мёртвого 82 → 83 → 85 %, потому что знаменатель уменьшается, а мёртвые байты нет). Мёртвое место создают перезаписи файлов от 4 КиБ до 1 МиБ, а не мелкие.
- **Read-modify-write.** Частичная запись в мелкий инлайн-файл идёт локально в индексе, а для объекта в пакете нужно прочитать его целиком (около 120 мс при холодном кэше по E9). Здесь это не измерялось.
- **Платим**: на каждый снимок (раз в 17 коммитов или чаще) в канал уходит весь заполненный бюджет, а монтирование скачивает его заново; индекс растёт, и `VACUUM INTO` под блокировкой записи дольше (на шум не списать только случай 64 МиБ). Цифры выше.

## Рекомендация

1. **Оставить `inline_max` = 4 КиБ и `inline_budget` = 16 МиБ.** Спека требует (17.2) в неоднозначном случае оставлять предварительные значения. Здесь они ещё и разумны: критерий 17.11 их пропускает с запасом более чем в 8 раз (худшая оценка 0,74 с на 1M при 4 КиБ и 16 МиБ против 6 с); 4 КиБ берёт три четверти от наибольшей экономии на `fsync` (−21 из −28), а следующий шаг до 8 и 16 КиБ добавляет пять и семь документов ценой дельты вдвое-втрое больше (C2: 120 → 246 → 399 КиБ на 100 файлов) и меньшего числа файлов на мегабайт бюджета; 16 МиБ — это вся C1 (1,9 МиБ) с большим запасом и 14 тысяч файлов C2.
2. **Бюджет больше 16 МиБ не оправдан**: 64 МиБ добавляют до 10 документов на C2 (0,2 %) и 3 на C4, снимок растёт на 48 МиБ (случайные данные) или на 6 МиБ (текст), монтирование на 2–3 с скачивания (расчёт).
3. **Бюджет 4 МиБ — равноценная альтернатива**, если важнее маленький снимок: на C1 при 4 КиБ все 1066 файлов влезают в 1,9 МиБ, критерий и экономия сообщений от него не меняются (одинаковая 4 КиБ/4 МиБ и 4 КиБ/16 МиБ в сообщениях на всех наборах, кроме C2: −0 вместо −6), а снимок C2 меньше на 12 МиБ. Данные не заставляют менять выбор, поэтому решение остаётся за предварительным значением.
4. **Инлайн выключать не нужно**: он работает без затрат по критерию и даёт ощутимую экономию на `fsync` мелких файлов и чтение без сети. Но аргумент «экономит сообщения» в спеке надо убрать: при пакетах инлайн сообщений почти не экономит.

## Ограничения

- Индекс собирается через `index_ops`, а не через `Vfs`: нет overlay, `fsync` на запись и путей `seal_file`. Для размеров снимка и дельты это не важно, для времени создания файлов важно, но оно здесь не мерилось.
- Содержимое C2 и C4 синтетическое (случайное и base64). Верхние оценки размеров снимка и дельты; для текста см. таблицу чувствительности. Настоящие файлы только у C1.
- Модель размеров C4 для E8 введена для этого эксперимента (SPEC 17.3 фиксирует доли, а не размеры). Выводы по C4 нужно читать как «индекс на миллион файлов с таким распределением», а не как реальное дерево.
- Время заливки и стоимость коммита рассчитаны, в Telegram не измерены (в этом эксперименте сети нет). Скорость 14 МиБ/с — для одного потока (E5), в режиме пользователя она предварительная.
- Время `VACUUM INTO`, zstd и шифрования шумное из-за параллельной нагрузки (см. «Окружение»); решение на этих секундах не держится: запас по критерию больше, чем разброс.
- Симуляция не включает чтение, кэш и `sync_timeout` (как E9). Сценарий с `fsync` — одна нагрузка C1 с долей 2 %, это чувствительность, а не прогноз.
- Правки инлайн-файлов — перезапись той же длины; рост и усечение, создание новых мелких файлов отдельно не мерились.
- C2 с `fsync`, C2 и C4 с переключениями не моделировались (нет событий).
- Режим пользователя (отдельный аккаунт) не затрагивается: эксперимент без сети.

## Что поправить в спеке (предложения, спеку не правил)

1. **17.11, итог E8** (новый абзац, как у E1 и E9): предварительные значения подтверждены (`inline_max` = 4 КиБ, `inline_budget` = 16 МиБ), все 16 комбинаций проходят критерий (худшая расчётная стоимость коммита 1,0 с при пороге 6 с, 2,3 с при занятом байтовом бакете), экономия сообщений относительно пакетов 0–10 документов (0,2 %) без `fsync` и −16 % документов при 4 КиБ с `fsync`.
2. **17.11, метод и решение**: (а) критерий «≤ 10 % от `commit_interval`» не отсекает ничего на сетке 4–64 МиБ; предлагаю писать, что он защищает от бюджета в сотни МиБ, и добавить условие «если все варианты проходят, а экономия сообщений различается меньше чем на 1 %, остаётся предварительное значение»; (б) время заливки снимка считается по E5, а не мерится; (в) метрику «сколько сообщений экономит инлайн» считать с `fsync` и без него: без него экономия 0.
3. **6.5, значения по умолчанию**: заменить «предварительные, их фиксирует E8» на «зафиксированы E8». Добавить в «Инлайн»: при заполненном бюджете инлайн получают первые по порядку запечатывания файлы, а не самые читаемые; снимок растёт на размер заполненного бюджета, для несжимаемых данных почти 1:1 (E8).
4. **17.3, C4**: «90 % пакетов, 5 % инлайн, 5 % позиционных» верно только при `inline_max` 4 КиБ; для E8 класс считается по порогам из модели размеров (5 % позиционных, остальные логарифмически равномерно от 16 Б до `pack_threshold`); `pack_threshold` в описании C4 — 4 МиБ (E9), а не 1 МиБ.
5. **17.12 (итог E9)**: фраза «инлайн при включённых пакетах почти не экономит сообщения» подтверждена E8 (0–10 документов на C2 при 5200), но с оговоркой про `fsync`: инлайн-файл не закрывает недобранный пакет.
6. **6.6 (`checkpoint_ratio`)**: E1 предлагал вернуться к `checkpoint_ratio` после E8. Возвращаться незачем: на C1 с инлайном цепочка закрывается после 2–3 дельт, стоимость 0,02–0,05 с на коммит.
7. **17.2 (инструменты)**: добавить `tgfs-e8`; в списке — `tgfs-sim` теперь знает отсрочку коммита (`--commit-defer`, SPEC 7.1).
8. **12.2**: комментарий к `inline_max` и `inline_budget` — «E8» вместо «предварительно» после п. 3.
