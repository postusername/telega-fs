# telega-fs: спецификация

Версия 0.5 (черновик), 2026-11-17. Это единственный источник правды по устройству системы: код, который с ним расходится, считается багом либо поводом сначала поправить спеку.

Слова **ДОЛЖНО**, **НЕ ДОЛЖНО**, **СЛЕДУЕТ** и **МОЖНО** используются в смысле RFC 2119.

---

## 1. Что это

FUSE-файловая система для Linux. Данные лежат в приватном Telegram-канале: файлы режутся на чанки, чанки шифруются на клиенте и загружаются документами, а индекс ФС (дерево, атрибуты, карта чанков) — это база SQLite, которая уходит в тот же канал зашифрованными снимками и дельтами; последний элемент закреплён.

### Цели v1

- Обычная POSIX-подобная ФС для одного пользователя: каталоги, файлы, переименование, частичная перезапись, `truncate`, `fsync`.
- Конфиденциальность: Telegram и любой, кто получил доступ к каналу, не видит ни содержимого, ни имён файлов, ни структуры каталогов.
- Целостность: подмена или порча любого чанка или индекса обнаруживается.
- Устойчивость к падениям: после краха процесса или машины ФС монтируется в последнем закоммиченном состоянии, без порчи.
- Ограниченные ресурсы: память не зависит от размера файлов, локальный диск ограничен настраиваемыми лимитами.
- Работа без сети: чтение из кэша и запись в staging, пока не исчерпан лимит.
- Мелкие файлы не стоят по сообщению на файл: самые мелкие лежат прямо в индексе, остальные мелкие собираются в пакеты (раздел 6.5).

### Не цели v1

- Несколько одновременных писателей (на разных машинах или в разных процессах).
- Жёсткие ссылки, xattr, ACL, `fallocate`, специальные файлы (FIFO, устройства, сокеты).
- macOS и Windows.
- Совместный доступ к одной ФС для нескольких пользователей Telegram.
- Роль единственной копии важных данных. Telegram не даёт гарантий хранения (см. раздел 13).

## 2. Факты о платформе, на которые опирается дизайн

Сверено с TDLib 1.8.70 (`td/generate/scheme/td_api.tl`, `td/telegram/MessageId.h`).

| Факт | Следствие |
|---|---|
| Идентификатор сообщения в TDLib — это серверный id, сдвинутый на 20 бит (`SERVER_ID_SHIFT = 20`). Сообщения с id `1` в TDLib не бывает. | Никаких «сообщений с известным номером». Голова ФС ищется через `getChatPinnedMessage`. |
| Текст сообщения ограничен 4096 символами, подпись документа — 1024. | Индекс хранится документом, а не текстом. |
| Документ до 2000 МиБ (у Premium до 4000 МиБ). | Размер чанка ограничен сверху, по умолчанию 16 МиБ. |
| `downloadFile` принимает `offset` и `limit`, `readFilePart` читает произвольный диапазон уже скачанного. | Чтение диапазона без скачивания всего чанка. Отсюда сегментное шифрование (раздел 5). |
| `sendMessage` сразу возвращает временное сообщение, итог приходит апдейтом `updateMessageSendSucceeded` или `updateMessageSendFailed`. | Загрузка асинхронная, ошибку **ДОЛЖНО** обрабатывать, иначе операция зависнет навсегда. |
| `pinChatMessage`, `unpinChatMessage` и `getChatPinnedMessage` (возвращает самое новое закреплённое) атомарны на стороне сервера. | Закрепление нового индекса и есть точка коммита. |
| `createNewSupergroupChat(..., is_channel=true, ...)` создаёт канал. | `init` сам создаёт канал, искать его по названию не нужно. |
| В `setTdlibParameters` есть `use_test_dc` и `database_encryption_key`. | E2E-тесты на тестовых серверах Telegram, локальная БД TDLib зашифрована. |
| `td_json_client_*` устарел, актуальный интерфейс — `td_create_client_id` / `td_send` / `td_receive` / `td_execute`. | Используем новый интерфейс. |
| Отправка сообщений лимитируется (`FLOOD_WAIT`, код 429, «retry after N»). | Собственный лимитер, ошибки 429 соблюдаются (раздел 10). |
| Бот входит через `checkAuthenticationBotToken` и работает по MTProto, поэтому лимиты HTTP Bot API (20 МБ на скачивание, 50 МБ на загрузку) к нему не относятся. | Бот-аккаунт годится как основной режим (раздел 10.3). |
| Бот не может создавать каналы, и `getChatHistory` ему недоступен. | В режиме бота канал создаёт пользователь, а обход истории заменяется перебором id через `getMessages` (раздел 4). |

## 3. Архитектура

```
             ┌──────────────────────────── telega-fs (один процесс) ────────────────────────────┐
  kernel ◄──►│ FuseFrontend (libfuse3, low-level API, многопоточный цикл)                       │
             │      │                                                                           │
             │      ▼                                                                           │
             │ Vfs ─────────► MetaStore (index.sqlite: дерево, экстенты, чанки)                 │
             │  │    │                                                                          │
             │  │    └──────► Overlay (state.sqlite + staging/: незалитые данные и атрибуты)    │
             │  ▼                                                                               │
             │ DataPath: ChunkReader (кэш, readahead) · ChunkWriter (seal → encrypt → upload)   │
             │           PackWriter (мелкие файлы → открытый пакет → upload)                    │
             │  │                                                                               │
             │  ▼                                                                               │
             │ CommitManager (снимки и дельты индекса, CAS по поколению, pin, отложенный GC)    │
             │  │                                                                               │
             │  ▼                                                                               │
             │ Store (интерфейс) ──► TelegramStore (TdClient, RateLimiter)                      │
             │                  └──► LocalDirStore (тесты, отладка, инъекция сбоев)             │
             │ Crypto (libsodium) · Keyring · Config                                            │
             │ ControlServer (ctl.sock: status, sync, snapshot)                                 │
             └──────────────────────────────────────────────────────────────────────────────────┘
```

Интерфейс `Store` намеренно узкий, чтобы почти всё тестировать без Telegram:

```cpp
struct ChunkRef { int64_t msg_id; std::string remote_file_id; };

class Store {
 public:
  virtual ChunkRef put_chunk(const std::filesystem::path& encrypted_file) = 0;
  virtual void     read_range(const ChunkRef&, uint64_t offset, std::span<std::byte> out) = 0;  // len = out.size()
  virtual void     delete_messages(std::span<const int64_t> msg_ids) = 0;  // чанки и блобы индекса

  // Голова ФС: последний закоммиченный блоб индекса (снимок или дельта).
  virtual std::optional<HeadInfo> read_head() = 0;            // msg_id + заголовок блоба
  virtual std::vector<std::byte>  read_index(int64_t msg_id) = 0;
  virtual int64_t put_index(const std::filesystem::path& blob) = 0;
  virtual void    set_head(int64_t new_msg_id, std::optional<int64_t> old_msg_id) = 0;  // pin new, unpin old
};
```

Все вызовы блокирующие с таймаутом и вызываются из рабочих потоков FUSE или фоновых очередей, но никогда из потока, который читает `td_receive`.

`HeadInfo` — это `msg_id` головы и её первые 256 байт (открытый заголовок блоба, раздел 6.3). Ошибки `Store` бросаются исключением `StoreError` с видом: `transient` (сеть, таймаут; повторяется), `not_found` (сообщения нет), `permanent` (остальное).

**LocalDirStore** хранит канал в локальном каталоге и используется в тестах, экспериментах и для отладки (профиль с `store = "local"`, раздел 12.2):

```
<dir>/
    next_id                 следующий msg_id (текст), начинается с 1
    msgs/<msg_id>           содержимое сообщения-документа, запись через tmp + rename
    pinned                  список закреплённых msg_id (текст, по одному в строке), запись через tmp + rename
```

- `msg_id` выдаются по возрастанию, как серверные id в канале. Сдвиг на 20 бит (раздел 2) не моделируется.
- `read_head` возвращает наибольший закреплённый `msg_id`, как `getChatPinnedMessage`.
- Инъекция сбоев задаётся программно (в тестах) или переменной окружения `TELEGA_FS_FAULTS` (в интеграционных тестах с бинарником): для каждой операции `Store` можно задать задержку, ошибку заданного вида на N-м вызове или «падение» — немедленное завершение процесса через `_exit` до или после выполнения операции. Формат переменной: правила через `;`, правило — `<операция>:<n>:<действие>`, где операция — `put_chunk`, `read_range`, `delete_messages`, `read_head`, `read_index`, `put_index`, `set_head`; `n` — номер вызова начиная с 1 или `*`; действие — `transient`, `permanent`, `crash_before`, `crash_after`, `delay=<мс>`.

## 4. Содержимое канала

Канал приватный, без участников, без публичной ссылки, с выключенным автоудалением. Им пользуется только telega-fs.

Сообщения в канале бывают трёх видов:

1. **Чанк данных.** Документ с именем `<16 случайных hex>.bin`, без подписи, `disable_content_type_detection = true`, `disable_notification = true`. Содержимое описано в разделе 5. Пакет мелких файлов (раздел 6.5) — тоже чанк данных того же формата, снаружи их не отличить.
2. **Блоб индекса** — снимок или дельта. Документ с именем `<16 случайных hex>.idx` и такими же флагами. Содержимое описано в разделе 6.3.
3. **Служебные сообщения Telegram** (создание канала, закрепления). Игнорируются.

**Голова ФС** — самое новое закреплённое сообщение канала. Оно **ДОЛЖНО** быть блобом индекса (снимком или дельтой). Если закреплённого сообщения нет, ФС считается неинициализированной.

telega-fs **НЕ ДОЛЖЕН** искать чанки поиском по каналу: любой чанк адресуется только по `msg_id` из индекса. Обход истории разрешён только в обслуживающих командах (`gc --deep`, `recover --scan`). В режиме пользователя это `getChatHistory`. В режиме бота это перебор: серверные id сообщений в канале идут подряд, поэтому диапазон от 1 до id последнего известного сообщения запрашивается через `getMessages` пачками по 100 с соблюдением лимитов (возможность проверяет эксперимент E3, раздел 17.6).

## 5. Формат чанка

Параметры ФС задаются при `init` и после этого не меняются:

- `chunk_size` (S): степень двойки от 1 МиБ до 256 МиБ, по умолчанию 16 МиБ.
- `segment_size`: 64 КиБ, фиксировано в формате v1.

Чанк — это до S байт открытого текста одной позиции файла (раздел 6.2). Зашифрованный файл чанка устроен так:

```
offset 0    header (40 байт)
            magic        "TGFSCHK1"        8
            version      u8 = 1            1
            reserved     7 нулевых байт    7
            chunk_nonce  16 случайных байт 16
            plain_size   u64 LE            8
offset 40   segment 0:  ciphertext(≤ 65536) || tag(16)
            segment 1:  ...
            segment n-1 (последний, может быть короче)
```

- Шифр: XChaCha20-Poly1305-IETF (`crypto_aead_xchacha20poly1305_ietf_*`), ключ `K_data` (раздел 11).
- Nonce сегмента `i` (24 байта): `chunk_nonce (16) || u64_le(i)`.
- Associated data сегмента `i`: `fs_uuid (16) || u64_le(chunk_id) || u64_le(i) || u8(is_last) || u64_le(plain_size)`. Это не даёт переставить сегменты, обрезать чанк или подменить один чанк другим.
- Сегмент `i` занимает в зашифрованном файле диапазон `[40 + i·65552, 40 + i·65552 + len_i + 16)`, поэтому для чтения диапазона открытого текста позиции считаются без скачивания чанка целиком.
- Ошибка проверки тега означает порчу: операция возвращает `EIO`, в лог пишется ошибка с `chunk_id` и `msg_id`, а `fsck` такой чанк помечает.
- `chunk_nonce` генерируется заново при каждой загрузке. Повторная загрузка того же содержимого даёт другой шифртекст.

## 6. Метаданные

### 6.1 Где что лежит

| Хранилище | Где | Что | Попадает в облако |
|---|---|---|---|
| `index.sqlite` | data-каталог профиля | Дерево, атрибуты, экстенты, чанки, ссылающиеся **только на уже залитые** чанки | да, снимками и дельтами |
| `state.sqlite` | data-каталог профиля | `base_generation`, overlay (грязные чанки и атрибуты), журнал загрузок, незалитые патчи, текущая цепочка | нет |
| `staging/` | data-каталог профиля | Открытый текст грязных чанков | нет |
| `tdfiles/` | cache-каталог профиля | Скачанные TDLib-ом зашифрованные чанки (кэш чтения) | нет |

Ключевой инвариант: **`index.sqlite` в любой момент согласован и ссылается только на чанки, которые уже лежат в канале.** Всё, что ещё не залито, живёт в overlay. Поэтому снимок индекса можно снять в любой момент, не дожидаясь окончания записи в открытые файлы.

### 6.2 Схема `index.sqlite`

```sql
PRAGMA journal_mode = WAL;
PRAGMA foreign_keys = ON;

CREATE TABLE meta (key TEXT PRIMARY KEY, value BLOB NOT NULL);
-- fs_uuid (BLOB 16 байт); INTEGER: format_version (=1), chunk_size, next_chunk_id, next_ino,
-- inline_max, inline_budget, pack_threshold, pack_target — параметры, неизменные после init;
-- inline_bytes — SUM(LENGTH(inline_data)) по всем inodes, ведётся в тех же транзакциях,
-- что меняют inline_data (бюджет проверяется за O(1)); сверяется при проверке индекса

CREATE TABLE inodes (
  ino       INTEGER PRIMARY KEY,           -- 1 = корень
  parent    INTEGER REFERENCES inodes(ino),-- NULL у корня и у открытых удалённых файлов
  name      BLOB,                          -- байты, 1..255, без '/' и '\0'
  kind      INTEGER NOT NULL,              -- 1 file, 2 dir, 3 symlink
  mode      INTEGER NOT NULL,              -- только биты прав (07777)
  uid       INTEGER NOT NULL,
  gid       INTEGER NOT NULL,
  size      INTEGER NOT NULL DEFAULT 0,    -- закоммиченный размер
  atime_ns  INTEGER NOT NULL,
  mtime_ns  INTEGER NOT NULL,
  ctime_ns  INTEGER NOT NULL,
  target    BLOB,                          -- цель symlink
  inline_data BLOB,                        -- содержимое инлайн-файла (раздел 6.5), иначе NULL
  UNIQUE (parent, name)
);

CREATE TABLE extents (
  ino       INTEGER NOT NULL REFERENCES inodes(ino) ON DELETE CASCADE,
  idx       INTEGER NOT NULL,              -- номер позиции: байты [idx·S, (idx+1)·S)
  chunk_id  INTEGER NOT NULL REFERENCES chunks(chunk_id),
  chunk_off INTEGER NOT NULL DEFAULT 0,    -- смещение в открытом тексте чанка; > 0 только у пакетов
  len       INTEGER NOT NULL,              -- сколько байт валидны начиная с chunk_off; дальше нули
  PRIMARY KEY (ino, idx)
);

CREATE TABLE chunks (
  chunk_id        INTEGER PRIMARY KEY,
  kind            INTEGER NOT NULL,        -- 1 позиционный чанк, 2 пакет
  msg_id          INTEGER NOT NULL,
  remote_file_id  TEXT,                    -- подсказка для getRemoteFile, может протухнуть
  plain_size      INTEGER NOT NULL,
  enc_size        INTEGER NOT NULL,
  content_mac     BLOB NOT NULL,           -- BLAKE2b-256 с ключом K_mac от открытого текста
  refcount        INTEGER NOT NULL,        -- число экстентов, ссылающихся на чанк
  live_bytes      INTEGER NOT NULL,        -- сумма len живых экстентов; для решения об уплотнении пакетов
  dead_since_gen  INTEGER                  -- NULL, пока refcount > 0
);
CREATE INDEX chunks_dead ON chunks(dead_since_gen) WHERE dead_since_gen IS NOT NULL;
CREATE INDEX chunks_mac  ON chunks(content_mac);

CREATE TABLE index_history (      -- все блобы индекса в канале, для уборки и восстановления
  generation INTEGER PRIMARY KEY,
  msg_id     INTEGER NOT NULL,
  blob_kind  INTEGER NOT NULL     -- 1 снимок, 2 дельта
);
```

У каждой таблицы есть `PRIMARY KEY`. Это обязательно: дельта-журнал (раздел 6.6) видит только таблицы с первичным ключом.

Правила:

- Отсутствующий экстент — это дыра, она читается нулями. Разреженные файлы и расширение через `truncate` бесплатны.
- Байт файла с позицией `p < size` читается из экстента `idx = p / S`: из его чанка по смещению `chunk_off + p % S`. Если `p % S ≥ len`, это ноль.
- У инлайн-файла нет экстентов, у файла с экстентами `inline_data IS NULL`.
- Уменьшение через `truncate` удаляет экстенты за концом, а у последнего частичного уменьшает `len`. Чанк не перезаливается, при этом после обратного расширения хвост гарантированно читается нулями.
- Число жёстких ссылок у файла всегда 1, у удалённого, но ещё открытого файла (`parent IS NULL`) — 0. У каталога `nlink = 2 + число подкаталогов`, значение вычисляется.

### 6.3 Блобы индекса: снимки и дельты

Индекс уходит в канал цепочками. **Цепочка** — это полный снимок, за которым идут от нуля до `max_chain` дельт. Каждый элемент цепочки — отдельное сообщение-документ (раздел 4). Каждый коммит добавляет ровно один элемент: либо дельту в текущую цепочку, либо снимок, который начинает новую. Голова ФС — последний элемент последней цепочки.

```
header (открытый, 256 байт, фиксированный размер)
  magic            "TGFSIDX1"          8
  version          u8 = 1              1
  blob_kind        u8                  1   -- 1 снимок, 2 дельта
  reserved         6
  fs_uuid          16
  generation       u64 LE              8
  snapshot_gen     u64 LE              8   -- поколение снимка, который начал цепочку; у снимка = generation
  snapshot_msg_id  i64 LE              8   -- msg_id снимка цепочки; у самого снимка 0
  prev_msg_id      i64 LE              8   -- предыдущий элемент цепочки; у снимка — бывшая голова или 0
  prev_hash        32                      -- BLAKE2b-256 всего блоба prev_msg_id; у снимка нули
  kdf_alg          u8                  1   -- 1 = argon2id13, 0 = keyfile (KDF нет, opslimit, memlimit и salt нулевые)
  kdf_opslimit     u64 LE              8
  kdf_memlimit     u64 LE              8
  kdf_salt         16
  wrapped_master   72                      -- secretbox: nonce(24) || mac(16) || master_key(32)
  body_size        u64 LE              8
  padding          нули до 256
body
  crypto_secretstream_xchacha20poly1305 (ключ K_index):
  заголовок потока (24 байта), затем блоки. Открытый текст режется на блоки по 1 МиБ,
  последний короче (но не пустой); у каждого блока +17 байт. Последний блок имеет тег
  TAG_FINAL, остальные — TAG_MESSAGE. Весь header (256 байт) передаётся как additional data
  в первый блок потока, у остальных блоков additional data нет. body_size — длина body
  в байтах, блоб целиком занимает 256 + body_size байт.
  Снимок: zstd(файл index.sqlite, полученный через VACUUM INTO).
  Дельта: zstd(chain || patchset), где
    chain    = u32 LE n, затем n × i64 LE msg_id — все предыдущие элементы цепочки по порядку, начиная со снимка;
    patchset = результат sqlite3session_patchset или sqlite3changegroup над несколькими такими патчами.
```

Правила:

- `generation` хранится только в заголовке. В самом `index.sqlite` поколения нет, поэтому один и тот же снимок можно повторно закоммитить с другим номером.
- Поколения в цепочке идут подряд: у k-й дельты `generation = snapshot_gen + k`.
- Заголовок аутентифицирован (он передаётся как additional data), поэтому `prev_hash` подменить нельзя. При монтировании хеш каждого скачанного элемента сверяется с `prev_hash` следующего. Перестановка, пропуск или подмена элемента цепочки — ошибка монтирования.
- Порядок цепочки защищает **только** `prev_hash` (и подряд идущие `generation`), а не сами патчи. В patchset у `UPDATE` нет старых значений, поэтому два патча, меняющие одни и те же строки, применятся в любом порядке без конфликта, и результат будет молча неверным. Конфликт при применении ловит лишь часть перестановок и пропусков. Проверку `prev_hash` и `generation` пропускать **НЕ ДОПУСКАЕТСЯ** ни в одном пути сборки индекса из цепочки (монтирование, `recover`).
- Параметры KDF и обёрнутый ключ лежат в каждом элементе, поэтому для расшифровки достаточно одной головы. Список `chain` в теле головы-дельты сразу даёт `msg_id` всех остальных элементов.

### 6.4 Схема `state.sqlite`

```sql
CREATE TABLE state (key TEXT PRIMARY KEY, value BLOB NOT NULL);
-- fs_uuid
-- base_generation, head_msg_id, head_hash  — последний успешный коммит
-- clean_shutdown  — 0 на время монтирования, 1 после корректного размонтирования
-- force_snapshot  — 1, если следующий коммит обязан быть снимком (раздел 6.6)
-- index_dirty     — 1, если index.sqlite менялся после последнего коммита

CREATE TABLE pending_patchsets (  -- забранные из сессии, но ещё не закоммиченные патчи
  seq INTEGER PRIMARY KEY,
  patchset BLOB NOT NULL
);

CREATE TABLE chain (              -- элементы текущей цепочки в канале
  pos INTEGER PRIMARY KEY,        -- 0 = снимок
  msg_id INTEGER NOT NULL,
  blob_size INTEGER NOT NULL
);

CREATE TABLE dirty_chunks (
  ino INTEGER NOT NULL, idx INTEGER NOT NULL,
  path TEXT NOT NULL,           -- файл в staging/
  version INTEGER NOT NULL,     -- растёт при каждой записи в чанк
  last_write_ns INTEGER NOT NULL,
  PRIMARY KEY (ino, idx)
);

CREATE TABLE dirty_attrs (      -- размер и время, которые ещё не дошли до index.sqlite
  ino INTEGER PRIMARY KEY, size INTEGER NOT NULL, mtime_ns INTEGER NOT NULL
);

CREATE TABLE upload_journal (   -- для уборки сирот после сбоя
  chunk_id INTEGER PRIMARY KEY,
  msg_id INTEGER,               -- NULL, пока загрузка не завершилась
  started_ns INTEGER NOT NULL
);

CREATE TABLE open_pack (        -- объекты открытого пакета (раздел 6.5)
  ino INTEGER PRIMARY KEY,
  version INTEGER NOT NULL,     -- version грязного чанка на момент добавления
  off INTEGER NOT NULL,
  len INTEGER NOT NULL
);
```

### 6.5 Мелкие файлы

Каждый файл в любой момент относится к одному из трёх классов хранения:

| Класс | Условие при запечатывании | Где данные |
|---|---|---|
| **Инлайн** | `size ≤ inline_max` и бюджет не исчерпан | `inodes.inline_data`, внутри зашифрованного индекса |
| **В пакете** | `size ≤ pack_threshold` | Один экстент `idx = 0` в чанке-пакете, `chunk_off > 0` допустим |
| **Позиционный** | Всё остальное | Экстенты по позициям, как в разделе 6.2 |

Класс выбирается заново при каждом запечатывании файла по его текущему размеру (раздел 8.1). Переход между классами делается одной транзакцией: новые данные записываются, старые освобождаются (`inline_data = NULL` или `refcount--` у старых экстентов). `pack_threshold ≤ S`, поэтому файл в пакете всегда умещается в одну позицию.

**Инлайн.**

- Запечатывание инлайн-файла ничего не загружает: в одной транзакции пишется `inline_data`, удаляются экстенты и очищается overlay. Данные попадают в облако со следующим коммитом индекса.
- Бюджет: `SUM(LENGTH(inline_data)) ≤ inline_budget`. Сумма хранится счётчиком `meta.inline_bytes`, а не считается проходом по `inodes`. Если запечатывание его превысило бы, файл идёт в пакет. Уже лежащие инлайн-файлы не выселяются.
- Чтение без сети и без кэша.

**Пакеты.**

- Пакет — это чанк `kind = 2` обычного формата (раздел 5). Внутри пакета нет своих заголовков и оглавления: объекты — просто диапазоны открытого текста, а вся адресация лежит в `extents`. Шифрование, проверка целостности и чтение диапазонов сегментами работают без изменений. Чтобы прочитать объект длиной `len`, расшифровываются не больше `⌈len / 64 КиБ⌉ + 1` сегментов.
- Открытый пакет один на всю ФС: `staging/pack-open` плюс таблица `open_pack`. При запечатывании мелкий файл дописывается в конец открытого пакета. Если файл уже лежит в открытом пакете, старый объект становится мёртвым, а новый пишется в конец.
- Пакет закрывается и заливается, когда выполнено одно из условий:
  - размер `≥ pack_target`;
  - возраст `≥ pack_max_age`;
  - `fsync` любого файла из пакета (`fsync` ждёт заливки пакета и коммита);
  - размонтирование;
  - давление на staging.
- После заливки одна транзакция: добавить чанк `kind = 2`, затем для каждого объекта, у которого `version` не изменилась, переставить экстент на пакет, сделать `refcount++` и добавить `len` к `live_bytes`, освободить старые данные и очистить overlay. Объекты, чей файл изменился за время заливки, не применяются: их новая версия уже в следующем открытом пакете, а занятые ими байты с самого начала мёртвые.
- При освобождении объекта `refcount--` и `live_bytes -= len`. Пакет с `refcount = 0` удаляется обычной отложенной уборкой (раздел 7.4).
- Уплотнение только вручную: `gc --compact` берёт пакеты с `live_bytes / plain_size < compact_ratio` (по умолчанию 0,25), скачивает их, переносит живые объекты в новый пакет и переставляет экстенты. Перепаковка всегда идёт в новый чанк с новым nonce. Хранилище бесплатное, поэтому автоматического уплотнения в v1 нет.
- Приватность: снаружи виден только размер пакета, ни число мелких файлов, ни их размеры не видны.
- Дедупликация (M4) в v1 работает только для позиционных чанков.
- Хвосты больших файлов в v1 в пакеты не кладутся: последний неполный чанк позиционного файла остаётся отдельным чанком. Формат (`chunk_off`) позволяет добавить это позже без миграции.

**До M3.** Пока нет PackWriter (веха M3), класс «в пакете» не используется: файл, который не стал инлайн, запечатывается как позиционный. Формат и схема от этого не меняются, после M3 такие файлы переходят в пакеты при следующем запечатывании.

Предварительные значения по умолчанию: `inline_max` = 4 КиБ, `inline_budget` = 16 МиБ, `pack_threshold` = 1 МиБ, `pack_target` = 16 МиБ, `pack_max_age` = 30 с. Окончательные фиксируют эксперименты E8 и E9 (раздел 17).

### 6.6 Дельта-журнал

Изменения `index.sqlite` между коммитами записывает SQLite session extension, своего формата операций нет.

- На писательском соединении MetaStore всегда открыта сессия `sqlite3session`, подключённая ко всем таблицам `index.sqlite`.
- Используется patchset, а не changeset. Для `UPDATE` в нём только первичный ключ и новые значения изменённых колонок, для `DELETE` — только ключ. Переименование каталога с 10 000 файлов — это одна изменённая строка.
- Перед первой записью в `index.sqlite` после коммита MetaStore ставит `index_dirty = 1` в `state.sqlite`. Исключение — служебные записи самого коммита и уборки: строка `index_history` (шаг 8 раздела 7.1) и удаление строк `chunks` отложенной уборкой (раздел 7.4). Они попадают в сессию и уходят со следующим коммитом, но сами `index_dirty` не ставят и коммит не запускают, иначе каждый коммит порождал бы следующий.
- Коммит-дельта забирает patchset под блокировкой записи и сразу пересоздаёт сессию. `VACUUM INTO` для дельты не нужен. Под блокировкой выполняются **только** забор патча и пересоздание сессии; запись патча в `pending_patchsets` идёт уже после того, как блокировка отпущена (E1: запись с `fsync` под блокировкой держала её до 300 мс). Порядок записи патчей в `pending_patchsets` совпадает с порядком забора. Если процесс упал между забором и записью, патч потерян, но это покрыто `clean_shutdown = 0` → `force_snapshot`; если запись не удалась без падения, ставится `force_snapshot = 1`.
- **Промежуточный забор.** Стоимость забора растёт линейно с числом изменённых строк (E1: около 0,8 мкс на строку на маленьком индексе и 2,3 мкс на 1M инодов). Чтобы забор держал блокировку единицы миллисекунд, MetaStore считает строки, изменённые с последнего забора, и при `patch_take_rows` (по умолчанию 2000) фоновый поток забирает патч в `pending_patchsets`, не дожидаясь коммита. Коммит склеивает все накопленные патчи как обычно. Промежуточный забор не делается, пока есть неподтверждённый pin (раздел 7.1), и при выставленном `force_snapshot` (патчи всё равно уйдут в снимок). Непустой промежуточный забор ставит `index_dirty = 1`, даже если в нём одни служебные записи: иначе патч лежал бы в `pending_patchsets` при «чистом» индексе. `base_generation` (и `dead_since_gen`) он не меняет.
- Забранный patchset до заливки записывается в `pending_patchsets`. Если коммит не удался, патч остаётся там, и следующая дельта склеивает все накопленные патчи по порядку через `sqlite3changegroup`. После успешного коммита включённые патчи удаляются.
- Сессия живёт только в памяти. Если процесс завершился нечисто, изменения после последнего забранного патча нельзя восстановить как дельту, поэтому следующий коммит **ДОЛЖЕН** быть снимком. Сам `index.sqlite` при этом согласован: его защищают транзакции SQLite.
- Применение при монтировании: открыть снимок, выключить `foreign_keys`, применить патчи цепочки по порядку через `sqlite3changeset_apply`, затем выполнить `PRAGMA foreign_key_check` и `PRAGMA integrity_check`. Обработчик конфликтов на любой конфликт возвращает `SQLITE_CHANGESET_ABORT`. Конфликт или проваленная проверка означают порчу, монтирование прерывается.

Коммит делает снимок, а не дельту, если выполнено одно из условий:

- выставлен `force_snapshot`: нечистое завершение, неудачный предыдущий снимок (раздел 7.1) или `mount --force-local`;
- в текущей цепочке уже `max_chain` дельт (по умолчанию 16);
- сумма размеров блобов дельт текущей цепочки (без новой) больше `checkpoint_ratio` от размера блоба её снимка (по умолчанию 0,25);
- это первый коммит после `init`.

Размонтирование отдельного снимка не требует, финальный коммит может быть дельтой.

Служебные записи (строка `index_history`, удаление строк `chunks` уборкой) не ставят `index_dirty`, поэтому, если после них не было коммита до размонтирования, они остаются только в локальном `index.sqlite` и в канал не попадают: сессия живёт в памяти. Это допустимо. Мёртвые строки `chunks` в канале безвредны (их сообщения уже удалены, а повторное удаление ничего не делает), а `index_history` сверяется при монтировании (раздел 7.2).

Значения зафиксированы экспериментом E1 (`docs/experiments/01-e1-patch-sizes.md`): `max_chain = 16`, `checkpoint_ratio = 0,25`, нижнего порога размера снимка нет. `max_chain` выбран при допущении о скорости скачивания 5–50 МБ/с и уточняется после E4.

**Известное ограничение до M3.** `VACUUM INTO` для снимка выполняется под блокировкой записи: около 13 мс на C1, 0,12 с на 100 тысяч инодов, около 1 с на миллион. Всё это время операции, меняющие метаданные, ждут; чтение не блокируется. Снимок из читательского среза без блокировки записи — задача M3.

## 7. Коммит, монтирование и восстановление

### 7.1 Коммит

Коммит запускается, если индекс изменился с прошлого коммита и выполнено одно из условий:

- прошло `commit_interval` (по умолчанию 60 с);
- с прошлого коммита залито `commit_every_chunks` чанков (по умолчанию 64);
- пришёл `fsync` или `fsyncdir`;
- идёт размонтирование.

Шаги (G — `base_generation`, H — `head_msg_id`):

1. Выбрать вид блоба: снимок или дельта (раздел 6.6).
2. Под блокировкой записи MetaStore:
   - для дельты забрать patchset и пересоздать сессию (запись в `pending_patchsets` — после блокировки, раздел 6.6);
   - для снимка выполнить `VACUUM INTO tmp/index-<G+1>.sqlite` и пересоздать сессию.

   Затем отпустить блокировку.
3. Собрать блоб (раздел 6.3) с `generation = G+1`, `prev_msg_id = H`, `prev_hash = head_hash`. Тело дельты — `sqlite3changegroup` всех `pending_patchsets` по порядку и список цепочки из `chain`. Сжать zstd (уровень 9 для снимка, 3 для дельты) и зашифровать.
4. **CAS-проверка:** прочитать голову канала (`getChatPinnedMessage` и её заголовок через `downloadFile` с `limit = 256`). Если `generation ≠ G` или `msg_id ≠ H`, значит ФС менял кто-то другой: коммит отменяется, монтирование переходит в read-only, в лог пишется ошибка.
5. Залить блоб, дождаться `updateMessageSendSucceeded`, получить `new_msg_id`.
6. `pinChatMessage(new_msg_id, disable_notification = true)`. **Это точка коммита.**
7. `unpinChatMessage(H)`. Если шаг не удался, ничего страшного: головой всё равно считается самое новое закреплённое сообщение.
8. Одной транзакцией в `state.sqlite`:
   - записать `base_generation = G+1`, `head_msg_id = new_msg_id`, `head_hash`, `index_dirty = 0`;
   - для дельты удалить включённые патчи и добавить элемент в `chain`;
   - для снимка удалить из `pending_patchsets` патчи, забранные до `VACUUM INTO` (позднее забранные остаются для следующей дельты), очистить `chain`, записать снимок первым элементом, сбросить `force_snapshot`. `VACUUM INTO` и промежуточный забор взаимно исключены, чтобы граница была однозначной.
   - `index_dirty` = есть записи после забора или в `pending_patchsets` остались патчи.

   В `index_history` добавить строку, она попадёт в следующий блоб.
9. Отложенная уборка (раздел 7.4).

Ошибки на шагах 3–6:

- **Не удалась дельта.** Патч остаётся в `pending_patchsets` и уйдёт со следующим коммитом.
- **Не удался снимок.** Выставляется `force_snapshot`: изменения, сделанные до `VACUUM INTO`, уже ушли из сессии, и следующая дельта их бы потеряла.

Неподтверждённый pin. Если `set_head` завершился транзиентной ошибкой (pin мог пройти) или упал шаг 8, попытка запоминается как неподтверждённая. Следующий коммит сначала читает голову: если голова — наш блоб, доделывается шаг 8, иначе залитый блоб удаляется. Блоб, залитый без pin при падении процесса между шагами 5 и 6, нигде не записан, его убирает только `gc --deep`.

Между шагами 4 и 6 остаётся окно гонки. Для однописательской модели это допустимо, защиту от двух писателей даёт локальный `flock` (раздел 12).

### 7.2 Монтирование

1. Разблокировать keyring (пароль или keyfile).
2. Поднять TDLib. Если сессия не авторизована, выйти с подсказкой запустить `telega-fs login`.
3. `getChat(chat_id)`: проверить доступ и что `message_auto_delete_time == 0`. Если автоудаление включено, **ДОЛЖНО** отказать в монтировании.
4. Прочитать голову: заголовок, затем тело. Проверить `magic`, `fs_uuid` и аутентичность. Если голова — дельта, взять из её тела список цепочки.
5. Если `clean_shutdown = 0`, прошлый сеанс завершился нечисто: выставить `force_snapshot = 1` (раздел 6.6).
6. Сравнить удалённое поколение `G_r` с локальным `G_l = base_generation`. **Локальные изменения** есть, если overlay не пуст, или `index_dirty = 1`, или `pending_patchsets` не пуста.

| Ситуация | Действие |
|---|---|
| Локального индекса нет, локальных изменений нет | Собрать индекс из цепочки головы (раздел 6.6), `G_l := G_r`. |
| Локального индекса нет, локальные изменения есть | Overlay без индекса не к чему применить: отказать (и в `--ro` тоже). С `--discard-local` (без `--ro`) — сбросить overlay и собрать индекс из цепочки. |
| `G_r == G_l` | Хеш и `msg_id` головы должны совпасть с `head_hash` и `head_msg_id`, иначе отказать как при порче. Взять локальный `index.sqlite`, догрузить грязные чанки из overlay. |
| `G_r > G_l`, локальных изменений нет | Если `G_l` входит в цепочку головы, применить к локальному индексу недостающие дельты. Иначе собрать индекс из цепочки целиком. |
| `G_r > G_l`, локальные изменения есть | Конфликт: отказать в rw-монтировании. Варианты: `--ro`, `--discard-local` или `recover --export-dirty <dir>`. |
| `G_r < G_l` | Откат головы (злоумышленник или ручное вмешательство): отказать. Варианты: `--ro` или `--force-local`, который следующим коммитом заливает локальный индекс снимком. |
| Голова пуста или не блоб индекса | Отказать с подсказкой про `init` или `recover --scan`. |

Особые случаи:

- **`G_r = G_l + 1` после падения между шагами 6 и 8 коммита.** Блоб головы узнаётся как свой по содержимому: у дельты `prev_hash` равен `head_hash`, список цепочки равен `chain`, а patchset равен склейке некоторого префикса `pending_patchsets` (промежуточный забор мог дописать патчи, пока блоб заливался); у снимка тело равно `tmp/index-<G>.sqlite`, который живёт до шага 8. Совпало — шаг 8 доделывается, и ситуация дальше разбирается как `G_r == G_l`. Не совпало — обычный конфликт `G_r > G_l`.
- **Догон дельтами.** После коммита поколения `G_l` в локальный индекс добавлена строка `index_history` для `G_l`, которой нет в блобе `G_l`, а следующая дельта везёт ту же строку. Поэтому перед применением дельт из копии локального индекса удаляются строки `index_history` с `generation ≥ G_l`. Любой конфликт при применении означает полную пересборку из цепочки.
- **Сверка `index_history`.** После любой сборки или выбора индекса в `index_history` добавляются отсутствующие строки для всех элементов текущей цепочки (служебная запись), иначе старые цепочки не убирались бы.
- **`--ro`** ничего не меняет ни в канале, ни локально: нет уборки сирот, удаления inode, `clean_shutdown` и коммитов. При конфликте или откате используется локальный индекс как есть.
- **`--force-local`**: новое поколение `G_l + 1`, CAS и `prev_msg_id` — против реальной головы. Монтирование ставит `force_snapshot = 1` и `index_dirty = 1`, чтобы снимок ушёл первым коммитом.
- **`--discard-local`** очищает overlay (`dirty_chunks`, `dirty_attrs`, `staging/`) и `pending_patchsets`, затем ведёт себя как «локального индекса нет». Порядок выбран так, чтобы крах на любом шаге не смешал поколения: если локальный индекс есть — сначала собрать новый индекс во временный файл и атомарно заменить, затем одной транзакцией сбросить локальные строки и записать состояние цепочки, затем очистить `staging/`; если индекса нет — сначала эта транзакция, затем сборка индекса, затем `staging/`.
- **Восстановление overlay при старте** (раздел 8.1) в `--ro` выполняется только в памяти: `state.sqlite` и `staging/` не меняются.

7. Убрать сирот из `upload_journal`: чанки с `msg_id`, на которые не ссылается ни индекс, ни overlay, удалить из канала. Чанки без `msg_id` (загрузка не дошла до конца) просто забыть.
8. Удалить inode с `parent IS NULL` (кроме корня): это файлы, удалённые при открытом дескрипторе до сбоя.
9. Записать `clean_shutdown = 0` и смонтировать FUSE.

**Размонтирование** (`destroy`): дождаться загрузок, сделать финальный коммит, записать `clean_shutdown = 1`. Если финальный коммит не удался (например, нет сети), `clean_shutdown = 1` всё равно записывается, но перед этим ставится `force_snapshot = 1`: изменения, ещё не забранные из сессии в `pending_patchsets`, вместе с сессией теряются, и следующая дельта их бы не содержала. Overlay при этом на диске, а сам `index.sqlite` согласован. Если ожидание загрузок (с учётом `sync_timeout`) или финальный коммит не удались, процесс пишет ошибку в лог и завершается с кодом 1.

### 7.3 Гарантии после сбоя

- После успешного возврата из `fsync(fd)` данные файла и его метаданные переживают сбой. Если заливка или коммит не уложились в `sync_timeout`, `fsync` возвращает `EIO` и ничего не гарантирует; данные при этом остаются в overlay и зальются позже.
- После успешного возврата из `fsyncdir` или `telega-fs sync` (управляющий сокет, M4) переживает сбой пространство имён (создания, удаления, переименования). Системный `sync(2)`/`syncfs(2)` до FUSE-ФС не доходит: в libfuse 3.10–3.14 нет операции `syncfs`, поэтому он ничего не гарантирует.
- В read-only режиме после CAS-конфликта `fsync`, `fsyncdir` и `sync` возвращают `EIO`: закоммитить данные нельзя. При монтировании с `--ro` они возвращают успех: изменений, которые надо сохранить, нет.
- Без `fsync` сбой может откатить состояние не дальше чем к последнему коммиту. Незакоммиченные, но залитые данные локально восстанавливаются из overlay и staging, если уцелел локальный диск.
- Частично записанный чанк, снимок или дельта никогда не видны как валидные: точка коммита одна — pin.

### 7.4 Отложенная уборка

- Когда `refcount` чанка падает до 0, ставится `dead_since_gen = G` (поколение, в котором чанк ещё был жив). После того как коммит забрал патч (шаг 2), но до шага 8, это `G + 1`: чанк ещё жив в забранном блобе. Новый чанк, на который ещё нет экстентов, сразу получает `dead_since_gen` (иначе пакет, все объекты которого устарели за время заливки, никогда не уберётся).
- Сообщение чанка удаляется (`deleteMessages`, `revoke = true`, пачками по 100), только когда `base_generation ≥ dead_since_gen + retain_generations` (по умолчанию 8). Порядок: запись `(chunk_id, msg_id)` в `upload_journal`, удаление строки `chunks` (служебная запись), `deleteMessages`, удаление записи журнала. Так сбой не оставит в индексе ссылку на удалённое сообщение, а сообщение, оставшееся после сбоя, уберёт уборка сирот при монтировании.
- Гарантия: последние `retain_generations` поколений полностью восстановимы. Более старые поколения могут ссылаться на уже удалённые чанки, даже если их блобы ещё лежат в канале.
- Блобы индекса удаляются целыми цепочками. Старая цепочка (снимок и все её дельты) удаляется, когда `base_generation ≥ g_last + retain_generations`, где `g_last` — поколение её последнего элемента. Из текущей цепочки ничего не удаляется.
- Пакеты подчиняются тем же правилам по `refcount`. Частично мёртвые пакеты сами не удаляются, их уплотняет только `gc --compact` (раздел 6.5).

## 8. Пути данных

### 8.1 Запись

`write(ino, off, data)` для каждой затронутой позиции `idx`:

1. Если чанк в overlay, писать в его файл в staging (`pwrite`) и увеличить `version`.
2. Иначе создать staging-файл:
   - если есть экстент и запись покрывает позицию не целиком, сначала скачать и расшифровать весь существующий чанк (read-modify-write);
   - если файл инлайн (это всегда позиция 0), скопировать в staging `inline_data`;
   - иначе создать разреженный файл с нулями.
3. Обновить `dirty_attrs` (размер и mtime).

Строка `dirty_chunks` пишется долговечно до возврата из `write`, а сам staging-файл синхронизируется только по `fsync`. Поэтому после отключения питания строка может пережить свой файл. Если при старте staging-файла нет, строка удаляется и позиция снова читается из индекса (откат не глубже последнего коммита, раздел 7.3), а ошибка видна в `status`. У инлайн-файла, который растёт за первую позицию, позиции `idx ≥ 1` применяются в индекс только после позиции 0: пока позиция 0 в overlay, остальные ждут, иначе индекс без overlay потерял бы и `inline_data`, и экстент 0. Если позиция 0 пропала (потерянный или пустой staging-файл), а у файла остались грязные позиции `idx ≥ 1` и непустой `inline_data`, позиция 0 заново создаётся в overlay из `inline_data`.

Пустой staging-файл (длина 0) не заливается: строка удаляется, и позиция читается из индекса, как при потерянном файле. Если файл был инлайн и стал пустым, `inline_data` очищается. `dirty_attrs` в обоих случаях сохраняются и переносятся в `inodes` обычным путём, когда грязных позиций у inode не осталось.

**Запечатывание и загрузка.** При запечатывании файла сначала по его размеру выбирается класс хранения (раздел 6.5). Инлайн-файлы и файлы для пакетов идут своим путём, ниже описан путь позиционного чанка. Чанк ставится в очередь загрузки, когда:

- писатель ушёл дальше по файлу: запись в `idx+1` при полностью записанном `idx` (потоковая заливка больших файлов);
- файл закрыт (`release`) — асинхронно, `close` не ждёт загрузки;
- пришёл `fsync(ino)` — синхронно, `fsync` ждёт загрузки и коммита, но не дольше `sync_timeout` (по умолчанию 300 с), затем `EIO`;
- с последней записи в чанк прошло `seal_delay` (по умолчанию 5 с);
- staging превысил `staging_high_watermark` — начиная с самых старых.

**Загрузка запечатанного чанка:**

1. Запомнить `version` и выделить `chunk_id` (`next_chunk_id++`).
2. Посчитать `content_mac`. Если в `chunks` уже есть чанк с тем же `content_mac` и `plain_size`, использовать его (`refcount++`) и пропустить шаги 3–4. Это **СЛЕДУЕТ** реализовать в M4.
3. Зашифровать в `tmp/`, записать в `upload_journal`, вызвать `Store::put_chunk`, записать `msg_id` в журнал.
4. В одной транзакции `index.sqlite`: добавить `chunks`, обновить экстент (`len` = валидная длина), у старого чанка сделать `refcount--`. Если у inode больше нет грязных чанков, перенести `dirty_attrs` в `inodes`; иначе поднять `inodes.size` до `max(size, idx·S + len)`, чтобы индекс без overlay не держал экстент за концом файла (после `truncate` вверх на другой машине ожил бы старый хвост). Валидная длина — не больше длины staging-файла: хвост из одних нулей не заливается, поэтому `plain_size` может быть меньше `min(S, size − idx·S)`. Сразу после транзакции убирается запись `upload_journal`.
5. Если `version` за время загрузки не изменилась, удалить staging-файл и запись в `dirty_chunks`. Иначе чанк остаётся грязным и будет залит снова.

**Обратное давление.** Если staging достиг `staging_limit` (по умолчанию 8 ГиБ), `write` блокируется, пока загрузки не освободят место. Если за `staging_full_timeout` (по умолчанию 300 с) место не освободилось (например, нет сети), возвращается `ENOSPC`.

### 8.2 Чтение

`read(ino, off, len)` для каждой позиции:

1. Чанк в overlay — читать из staging.
2. Инлайн-файл — читать `inline_data`.
3. Экстента нет — нули.
4. Иначе вычислить нужные сегменты чанка с учётом `chunk_off` и их зашифрованный диапазон, затем:
   - получить `file_id`: `getRemoteFile(remote_file_id)`, при неудаче `getMessages(chat_id, [msg_id])` и обновить `remote_file_id`;
   - `downloadFile(file_id, priority, offset, limit, synchronous = true)`;
   - `readFilePart(file_id, offset, count)`;
   - расшифровать сегменты и положить их в RAM-кэш открытого текста (LRU, `plain_cache` = 64 МиБ).
5. Обрезать по `len` экстента и по размеру файла.

**Readahead.** Если чтения последовательные, асинхронно подгружать следующие `readahead` байт (по умолчанию 4 МиБ, с удвоением до 32 МиБ).

**Кэш чтения на диске** — это файлы TDLib в `tdfiles/`. telega-fs учитывает их размер и время доступа и при превышении `cache_limit` (по умолчанию 4 ГиБ) вызывает `deleteFile(file_id)` для самых давно использованных.

**Без сети** чтение данных, которых нет в кэше, ждёт до `read_timeout` (по умолчанию 60 с) и затем возвращает `EIO`.

## 9. FUSE

Используется **low-level API** libfuse3: адресация по inode, корректные `lookup` и `forget`, нормальный `rename` без пересчёта путей. Цикл многопоточный. Опции монтирования по умолчанию: `default_permissions`, `fsname=telega-fs`, `subtype=telega-fs`.

| Операция | Поведение |
|---|---|
| `init` / `destroy` | `destroy` делает финальный коммит с ожиданием всех загрузок. |
| `lookup`, `forget`, `getattr` | Атрибуты из `inodes`, поверх них `dirty_attrs`. Размер блока 4096, `st_blocks` = размер, округлённый вверх. |
| `setattr` | chmod, chown (только хранится), truncate (раздел 6.2), utimens. |
| `mkdir`, `rmdir` | `rmdir` непустого каталога возвращает `ENOTEMPTY`. |
| `create`, `open`, `release` | `O_TRUNC` эквивалентен `truncate(0)`. `O_APPEND` поддерживается ядром через `getattr`. |
| `read`, `write`, `flush`, `fsync` | Раздел 8. |
| `unlink` | Убирает запись из каталога. Если файл открыт, inode живёт с `parent = NULL` до последнего `release` или `forget`, затем экстенты освобождаются (`refcount--`). |
| `rename` | Атомарно в одной транзакции. Поддерживается `RENAME_NOREPLACE`. `RENAME_EXCHANGE` возвращает `EINVAL`. Перезапись непустого каталога — `ENOTEMPTY`. |
| `symlink`, `readlink` | Поддерживаются, цель хранится в `target`. |
| `opendir`, `readdir(plus)`, `releasedir`, `fsyncdir` | `readdir` отдаёт записи по возрастанию `name`. Продолжение — курсор по имени (`name > последнее отданное`), смещение для ядра — порядковый номер записи в потоке каталога, соответствие номера и имени хранится в дескрипторе каталога. `fsyncdir` вызывает коммит. |
| `statfs` | `f_blocks` из `virtual_capacity` (по умолчанию 1 ПиБ), `f_bfree` = `virtual_capacity` − занято, `f_namemax` = 255. |
| `link` | `EPERM`. |
| `mknod` не для обычного файла | `EPERM`. |
| xattr | Не поддерживаются: обработчики не регистрируются, ядру уходит `ENOSYS`, оно его запоминает, приложение видит `ENOTSUP`. |
| `fallocate` | `EOPNOTSUPP`. |

Ошибки: `ENOENT`, `EEXIST`, `ENOTDIR`, `EISDIR`, `ENOTEMPTY`, `ENAMETOOLONG`, `EROFS` (read-only режим), `ENOSPC` (staging), `EIO` (сеть, таймаут, порча), `EPERM`, `ENOTSUP`.

Внутренняя конкурентность:

- MetaStore: одно писательское соединение SQLite под мьютексом, читательские соединения на поток (WAL).
- Структуры overlay под `std::shared_mutex`.
- Блокировки берутся в порядке MetaStore → Overlay → кэш. Вызов `Store` при удерживаемой блокировке MetaStore **НЕ ДОПУСКАЕТСЯ**.

## 10. Работа с Telegram

### 10.1 TdClient

- Интерфейс `td_create_client_id` / `td_send` / `td_receive` / `td_execute`.
- Один поток читает `td_receive` и только разбирает и диспетчеризует ответы. Блокирующая работа в обработчиках **НЕ ДОПУСКАЕТСЯ**.
- Запросы получают `@extra = <u64 id>`, ответ резолвит `std::promise`. Таблица ожидающих запросов под мьютексом.
- Апдейты маршрутизируются по типу: `updateAuthorizationState`, `updateMessageSendSucceeded` и `updateMessageSendFailed` (по `old_message_id`), `updateFile` (прогресс загрузок и скачиваний).
- У каждого запроса таймаут. По истечении promise получает ошибку, а запоздавший ответ отбрасывается.
- Лог TDLib: `setLogStream(logStreamFile, max_file_size = 16 МиБ)`, уровень 1, файл в data-каталоге профиля.
- `setTdlibParameters`: `use_test_dc` из профиля, `database_directory = <data>/tdlib`, `files_directory = <cache>/tdfiles`, `database_encryption_key` из keyring, `use_message_database = false`, `use_secret_chats = false`, `device_model = "telega-fs"`, `application_version` = версия telega-fs.

### 10.2 Лимиты и ошибки

- Параллельных загрузок `upload_concurrency` (по умолчанию 2), параллельных скачиваний `download_concurrency` (по умолчанию 4).
- Token bucket на отправку сообщений в канал: `send_rate` (по умолчанию 20 в минуту, всплеск до 5).
- Значения `upload_concurrency` и `send_rate` предварительные. Для каждого режима их фиксирует эксперимент E5 (раздел 17.8).
- Ошибка 429 или `FLOOD_WAIT` с «retry after N» приостанавливает все отправки на N секунд (плюс случайный джиттер до 10 %). Обход ограничения через параллельные соединения **НЕ ДОПУСКАЕТСЯ**.
- Сетевые и 5xx-ошибки повторяются с экспоненциальной задержкой от 1 до 60 с, бесконечно для фоновых загрузок и до `read_timeout` для синхронных чтений.
- Синхронные операции, которые ждут заливки и коммита (`fsync`, `fsyncdir`, `sync`, команда `sync` управляющего сокета, ожидание загрузок при размонтировании), ждут не дольше `sync_timeout` (по умолчанию 300 с) и затем возвращают `EIO` (команда сокета — ошибку `timeout`). Фоновые повторы при этом продолжаются. Размонтирование по истечении `sync_timeout` всё равно делает попытку финального коммита и пишет `clean_shutdown = 1`: незалитое остаётся в overlay.
- 400-е ошибки (кроме 429) не повторяются. Чанк остаётся в overlay, ошибка пишется в лог и видна в `status`.

### 10.3 Авторизация: два режима

Режим задаётся в профиле (`auth = "bot" | "user"`). Форматы чанков и индекса в обоих режимах одинаковые, поэтому профиль можно переключить на другой режим без миграции данных: достаточно, чтобы новый аккаунт имел нужные права в канале.

**Бот (рекомендуемый, по умолчанию).**

- Пользователь создаёт бота у @BotFather, своим аккаунтом создаёт приватный канал и добавляет туда бота администратором с правами публиковать, редактировать, удалять и закреплять сообщения. Минимальный набор прав определяет эксперимент E2 (раздел 17.5).
- `telega-fs login --bot`: ввод токена, `checkAuthenticationBotToken`. Свой `api_id` нужен и здесь.
- `init` работает только с `--chat <id>`, потому что бот не создаёт каналы.
- Почему рекомендуем: при блокировке банят только бота, а канал и данные остаются у пользователя. Восстановление: новый бот в тот же канал или переключение профиля в режим пользователя.
- Чем платим: ручная настройка канала, перебор вместо `getChatHistory` в обслуживающих командах, вероятно более жёсткие лимиты на отправку (по FAQ Bot API порядка 20 сообщений в минуту на группу, для каналов меряется в E5, раздел 17.8).
- Голова ФС ищется так же, через `getChatPinnedMessage`. Если эксперимент E2 покажет, что бот не может закреплять сообщения или читать закреплённое, запасной вариант — хранить `msg_id` головы в описании канала (`setChatDescription`). Тогда раздел 7.1 правится до начала реализации.

**Пользователь.**

- `telega-fs login`: интерактивно телефон, код, пароль 2FA. **МОЖНО** добавить вход по QR (`requestQrCodeAuthentication`).
- `init` без `--chat` создаёт канал сам.
- **СЛЕДУЕТ** использовать отдельный аккаунт, не основной (раздел 13).

В обоих режимах после входа монтирование ничего не спрашивает, кроме пароля keyring (если не задан keyfile).

## 11. Криптография и ключи

Модель угроз:

- **Защищаемся от** Telegram и любого, кто читает канал: содержимое, имена, структура и точные размеры файлов скрыты. Размеры чанков видны, поэтому порядок размера файла частично утекает, и это принято. Подмена данных обнаруживается. Откат головы обнаруживается по локальному `base_generation`.
- **Не защищаемся от** скомпрометированной локальной машины и от потери доступности (удаление канала, бан аккаунта).

Ключи:

- `master_key`: 32 случайных байта, создаётся при `init`.
- Подключи через `crypto_kdf_derive_from_key`, контекст `"TGFS_KDF"`: id 1 — `K_data`, id 2 — `K_index`, id 3 — `K_mac`.
- `KEK = Argon2id(passphrase, kdf_salt, OPSLIMIT_MODERATE, MEMLIMIT_MODERATE)`. `master_key` хранится обёрнутым (`crypto_secretbox_easy`) в заголовке каждого блоба индекса (раздел 6.3) и в локальном keyring.
- Вместо пароля **МОЖНО** использовать keyfile (32 случайных байта), тогда `KEK = keyfile`.
- Параметры KDF из заголовка блоба (на машине без keyring) не аутентифицированы до расшифровки, поэтому принимаются только в пределах `OPSLIMIT_SENSITIVE` и `MEMLIMIT_SENSITIVE`, иначе отказ: подложенный блоб не должен заставлять Argon2 выделять произвольную память.
- `telega-fs passwd` перешифровывает `master_key` новым KEK, обновляет keyring и делает коммит.
- **Потеря пароля или keyfile означает потерю данных.** Об этом **ДОЛЖНО** предупреждать при `init`.

Локальный keyring (`<data>/keyring`, права 0600): обёрнутые `master_key` и `tdlib_db_key` (32 случайных байта для `database_encryption_key`). Формат, 256 байт, запись через tmp + `fsync` + rename:

```
magic          "TGFSKEY1"   8
version        u8 = 1       1
kdf_alg        u8           1   -- как в заголовке блоба индекса (раздел 6.3)
reserved       6
fs_uuid        16
kdf_opslimit   u64 LE       8
kdf_memlimit   u64 LE       8
kdf_salt       16
wrapped_master 72               -- secretbox(KEK): nonce(24) || mac(16) || master_key(32)
wrapped_tdlib  72               -- secretbox(KEK): nonce(24) || mac(16) || tdlib_db_key(32)
padding        нули до 256
```

Неверный пароль или keyfile обнаруживается по ошибке проверки `wrapped_master` и выдаётся как «неверный пароль», без подробностей.

Секреты (ключи, `api_hash`, пароль, номер телефона, auth key) **НЕ ДОЛЖНЫ** попадать в логи, сообщения об ошибках и дампы. Имена файлов пишутся в лог только на уровне `debug`.

### 12.3 Команды

| Команда | Что делает |
|---|---|
| `telega-fs login [-p P] [--bot] [--test-dc]` | Вход в Telegram для профиля: токен бота или телефон пользователя (раздел 10.3). |
| `telega-fs logout [-p P]` | Выход и удаление сессии. |
| `telega-fs init [-p P] (--chat ID \| --title T) [--chunk-size 16M] [--keyfile F]` | Берёт пустой существующий канал (`--chat`, единственный вариант для бота) или создаёт новый (`--title`, только для пользователя). Создаёт ключи и пустой индекс поколения 1, закрепляет его. |
| `telega-fs mount [-p P] DIR [-f] [--ro] [-o OPTS]` | Монтирование (раздел 7.2). |
| `telega-fs status [-p P]` | Поколение, длина цепочки, грязные байты, очередь загрузок, последние ошибки. Если ФС смонтирована — через управляющий сокет, иначе чтением `state.sqlite`. |
| `telega-fs sync [-p P]` | Дождаться заливки всех грязных данных и коммита. Только для смонтированной ФС, через управляющий сокет. |
| `telega-fs fsck [-p P] [--repair] [--verify-data]` | Согласованность индекса, существование всех `msg_id` (`getMessages` пачками по 100), с `--verify-data` ещё и проверка тегов всех чанков. |
| `telega-fs gc [-p P] [--deep] [--compact]` | Отложенная уборка. С `--deep` — обход истории канала и удаление сообщений, на которые никто не ссылается. С `--compact` — уплотнение пакетов (раздел 6.5). |
| `telega-fs passwd [-p P]` | Смена пароля или keyfile. |
| `telega-fs recover [-p P] --scan \| --export-dirty DIR` | Поиск блобов индекса в истории, если голова потеряна: берётся самая длинная целая цепочка с наибольшим поколением. Выгрузка незакоммиченных данных при конфликте. |

Остальные обслуживающие команды при смонтированной ФС отказываются работать: `lock` захвачен процессом монтирования.

Профиль с `store = "local"` не требует `api_id`, `login` и TDLib: `init` вызывается без `--chat` и `--title` и пишет в `local_dir`, `mount` работает с ним так же, как с каналом. Пути XDG берутся из `XDG_CONFIG_HOME`, `XDG_DATA_HOME` и `XDG_CACHE_HOME`, если они заданы; интеграционные тесты так изолируют профиль во временном каталоге. Все команды принимают `--config FILE` вместо `~/.config/telega-fs/config.toml`.

### 12.4 Управляющий сокет

Смонтированная ФС принимает команды через unix-сокет `<data>/ctl.sock`.

- Сокет создаётся при монтировании с правами 0600 в каталоге 0700 и удаляется при размонтировании. Оставшийся от упавшего процесса сокет удаляется при следующем монтировании, после того как захвачен `lock`.
- При каждом подключении процесс-собеседник проверяется через `SO_PEERCRED`: его uid должен совпадать с uid процесса telega-fs, иначе соединение закрывается.
- Протокол: одна JSON-строка запроса — одна JSON-строка ответа. Запрос `{"proto": 1, "cmd": "<имя>", "args": {...}}`, ответ `{"proto": 1, "ok": true, "result": {...}}` или `{"proto": 1, "ok": false, "error": {"code": "...", "message": "..."}}`. Неизвестная версия протокола или команда — ошибка с кодом `unsupported`.
- Команды v1:
  - `status` — то же, что выводит `telega-fs status`;
  - `sync` — заливает все грязные данные и делает коммит, отвечает после коммита или ошибки;
  - `snapshot` — следующий коммит делается снимком, отвечает после этого коммита.
- Через сокет не передаются секреты, и он не даёт выполнить ничего, чего не может сам пользователь.

## 13. Правила эксплуатации и Telegram ToS

Опираемся на [Telegram API Terms of Service](https://core.telegram.org/api/terms). Хранение файлов там не запрещено, но есть общие требования. telega-fs **ДОЛЖЕН**:

- использовать собственный `api_id` пользователя (п. 2.1). В репозитории `api_id` и `api_hash` не хранятся;
- не использовать слово «Telegram» в названии приложения (п. 2.3). `device_model` и `application_version` честные;
- выполнять действия только по явному запуску пользователем (п. 1.4) и ничего не делать вне своего канала.

Практика, которая снижает риск блокировки антиспамом:

- **Режим бота** (раздел 10.3) как рекомендуемый: под удар попадает бот, а не аккаунт пользователя.
- В режиме пользователя — **отдельный аккаунт** под хранилище, не основной.
- Лимиты из раздела 10.2 по умолчанию консервативные. Повышать их **СЛЕДУЕТ** только осознанно.
- Документация **ДОЛЖНА** прямо говорить: Telegram не даёт гарантий хранения, канал или аккаунт могут пропасть, telega-fs не заменяет резервную копию.

## 14. Тестирование

- **Юнит-тесты (GoogleTest):** криптография (round-trip, порча каждого поля, границы сегментов, последний сегмент, пустой хвост), арифметика экстентов, `chunk_off` и `len`, операции MetaStore, overlay, машина состояний монтирования (все строки таблицы из 7.2). Классы хранения: все переходы между тремя классами, исчерпание инлайн-бюджета, изменение файла во время заливки его пакета, уплотнение.
- **Дельта-журнал:** property-тест — случайная последовательность операций ФС с коммитами в случайные моменты, затем индекс собирается из цепочки и сравнивается с живым построчно. Отдельно: склейка нескольких `pending_patchsets`, порча, перестановка и пропуск элемента цепочки, неудавшийся снимок с последующей дельтой.
- **Инъекция сбоев:** `LocalDirStore` умеет задержки, ошибки и «падение» на заданном шаге коммита или загрузки. Тест прогоняет сбой на каждом шаге 7.1 и 8.1 и проверяет, что после перезапуска ФС согласована и соответствует гарантиям 7.3.
- **Интеграционные FUSE-тесты** на `LocalDirStore` во временном каталоге. Без `/dev/fuse` они пропускаются через `GTEST_SKIP`, а не считаются пройденными. На раннерах GitHub `/dev/fuse` есть, поэтому в CI они выполняются. Длинные прогоны fsx помечены меткой `long` и в CI не запускаются (`ctest -LE long`), только вручную: `ctest -L long`. `fsx` — собственная реализация в `tests/integration/fsx` по модели fsx из xfstests: случайные `read`, `write`, `truncate`, `mmap`-чтение и запись, `fsync`, закрытие и повторное открытие файла со сверкой с моделью в памяти, фиксированный seed и журнал последних операций при расхождении (не меньше 100 000 операций без расхождений, плюс прогон с перемонтированием посередине). Сценарии: большой последовательный файл, случайные перезаписи, rename поверх, unlink открытого файла, перемонтирование, работа без сети (через `TELEGA_FS_FAULTS`). Также подмножество `pjdfstest` по поддерживаемым операциям.
- **E2E на тестовых серверах Telegram** (`use_test_dc`, тестовые номера по [core.telegram.org/api/auth](https://core.telegram.org/api/auth), бот заводится у @BotFather тестового DC): `init`, запись 200 МиБ, размонтирование, монтирование с пустым кэшем на «другой машине», сверка sha256. Прогоняется в обоих режимах авторизации, плюс переключение профиля из режима бота в режим пользователя на том же канале. Запускается вручную или по расписанию, не на каждый push.
- **Сборки с санитайзерами:** ASan+UBSan и TSan в CI (раздел 15.4).

## 15. Стек и сборка

Язык — C++20 (решено 2026-11-16). Платформы — Linux x86_64 и aarch64.

### 15.1 Зависимости

| Зависимость | Версия | Откуда |
|---|---|---|
| Компилятор | C++20: Clang ≥ 17 или GCC ≥ 13 | система |
| CMake, Ninja | CMake ≥ 3.25 (нужен `SYSTEM` у `FetchContent_Declare`) | система |
| libfuse3 | ≥ 3.10 | система |
| libsodium | ≥ 1.0.18 | система |
| zstd | ≥ 1.5 | система |
| OpenSSL, zlib | поддерживаемые дистрибутивом | система, нужны TDLib |
| TDLib | 1.8.70, коммит `ba976cb4aba53a82eff425db2f85e2741774c944` | собирается отдельно (15.3) |
| SQLite | актуальный релиз на момент M0 | amalgamation через `FetchContent` (15.2) |
| nlohmann_json, toml++, CLI11, spdlog, GoogleTest | актуальные релизы на момент M0 | `FetchContent` |

- Всё, что идёт через `FetchContent`, описано в `cmake/deps.cmake`: URL релизного архива и `URL_HASH SHA256=...`. Системные копии этих библиотек не используются, чтобы сборка была одинаковой везде. Обновление зависимости — отдельный коммит.
- Офлайн-сборка: `FETCHCONTENT_FULLY_DISCONNECTED=ON` и заранее заполненный `FETCHCONTENT_BASE_DIR`.

### 15.2 SQLite

Своя статическая библиотека `telega_sqlite` из amalgamation с флагами:

- `SQLITE_ENABLE_SESSION`, `SQLITE_ENABLE_PREUPDATE_HOOK` — для дельта-журнала (раздел 6.6);
- `SQLITE_THREADSAFE=2` — соединение на поток, общих соединений между потоками нет (раздел 9);
- `SQLITE_DQS=0`, `SQLITE_DEFAULT_MEMSTATUS=0`, `SQLITE_OMIT_DEPRECATED`, `SQLITE_OMIT_LOAD_EXTENSION`, `SQLITE_LIKE_DOESNT_MATCH_BLOBS`.

Почему не системная: наличие session extension в дистрибутивах не гарантировано, а формат патчей и поведение `VACUUM INTO` лучше держать на одной версии. TDLib собирает свою копию SQLite с переименованными символами (`tdsqlite3_*`), так что конфликтов при линковке нет.

### 15.3 TDLib

- Собирается отдельно по инструкции из README в свой префикс. Локально это `./td/tdlib`, каталог в `.gitignore`.
- CMake: `find_package(Td 1.8.70 EXACT REQUIRED)`, путь задаётся через `-DTd_DIR=<prefix>/lib/cmake/Td`.
- Линкуется `Td::TdJsonStatic`: получается один бинарник, без `libtdjson.so` рядом.
- TDLib собирается со стандартной библиотекой по умолчанию (libstdc++) и без `TD_ENABLE_LTO`. Сборка с `-stdlib=libc++` или с LTO даёт архивы, которые не линкуются GCC (биткод LLVM) и тянут лишнюю динамическую зависимость (раздел 15.4).
- Обновление TDLib — отдельный коммит: новый хеш в README, в этой спеке и в `.github/workflows/ci.yml`, прогон E2E. Полный хеш коммита 1.8.70 — `ba976cb4aba53a82eff425db2f85e2741774c944`.
- В CI установленный префикс TDLib кэшируется по хешу коммита: сборка TDLib идёт десятки минут и требует 2–3 ГБ RAM на поток.

### 15.4 Конфигурации сборки

`CMakePresets.json`, генератор Ninja:

| Пресет | Тип сборки | Для чего |
|---|---|---|
| `dev` | Debug | Локальная разработка, предупреждения не ломают сборку |
| `ci` | RelWithDebInfo, `-Werror` | Основная сборка в CI |
| `asan` | Debug, ASan + UBSan | CI |
| `tsan` | Debug, TSan | CI. Гоняет тесты на `LocalDirStore`: TDLib не инструментирован и в этих тестах не участвует. Исключение — `telega_fs.version`, он вызывает синхронный `td_execute` без потоков TDLib |
| `release` | Release, LTO | Бинарник для установки |

- Предупреждения: `-Wall -Wextra -Wpedantic -Wshadow -Wconversion`, в `ci` плюс `-Werror`.
- Определения: `_FILE_OFFSET_BITS=64`, `FUSE_USE_VERSION=310` (API libfuse 3.10, минимальной поддерживаемой версии; зафиксировано в M0).
- Опции: `TELEGA_FS_BUILD_TESTS` (по умолчанию ON), `TELEGA_FS_E2E` (по умолчанию OFF, E2E нужен тестовый аккаунт и сеть), `TELEGA_FS_BUILD_TOOLS` (по умолчанию OFF, раздел 17.2), `TELEGA_FS_WERROR` (включается пресетом `ci`).
- Пресеты по умолчанию ищут TDLib в `${sourceDir}/td/tdlib/lib/cmake/Td`, другой путь задаётся через `-DTd_DIR=...`.
- Санитайзеры включаются флагами компилятора на весь проект, включая зависимости из `FetchContent`, чтобы TSan видел всё, что запускают тесты.
- Юнит-тесты не линкуются с TDLib: они собираются из библиотеки `telega_core`, а TDLib подключается только к бинарнику `telega-fs`.
- `CMAKE_EXPORT_COMPILE_COMMANDS=ON` для clangd и clang-tidy.
- Результат — один бинарник `telega-fs`. Динамически он линкуется только с системными libfuse3, libsodium, libzstd, libssl, libcrypto и libz, плюс libc, libm, libstdc++, libgcc_s и части glibc, которые до 2.34 были отдельными библиотеками (libdl, libpthread, librt). В сборках с санитайзерами дополнительно допускаются их рантаймы и libresolv. Это проверяет тест `telega_fs.linkage` (`tools/ci/check-linkage.sh`).
- Подавления LeakSanitizer лежат в `tools/ci/lsan.supp` и допускаются только для кода, который мы не контролируем (TDLib, зависимости). Каждое правило узкое и с причиной.

### 15.5 Инструменты

- `.clang-format` и `.clang-tidy` в корне. CI проверяет форматирование и прогоняет clang-tidy на изменённых файлах. Версия clang-format и clang-tidy — 18 (Ubuntu 24.04).

### 15.6 CI

- GitHub Actions, `ubuntu-24.04`, запуск на push в `main`, на pull request и вручную.
- Задача `tdlib` собирает TDLib (clang, Release) и сохраняет установленный префикс в кэш с ключом по полному хешу коммита TDLib, образу раннера и версии рецепта сборки. Остальные задачи кэш только восстанавливают.
- Группа `concurrency` включает тип события. Отменяются только устаревшие прогоны pull request. Ручной запуск и push в `main` поэтому идут параллельно. Если кэша TDLib ещё нет, его соберут оба, поэтому первый прогон запускается чем-то одним. Первый прогон на пустом кэше TDLib **СЛЕДУЕТ** делать в `main`: кэш, сохранённый в pull request, виден только этому pull request.
- Раз в неделю по расписанию запускается только задача `tdlib` и восстанавливает кэш: GitHub удаляет кэши, к которым не обращались 7 дней, а пересборка TDLib стоит больше часа.
- Сборка идёт через ccache, кэш отдельный для каждой пары «пресет, компилятор». Сохраняется он только на push в `main`, pull request его только читает. После прогона в `main` отдельная задача оставляет только самую новую запись ccache каждой пары, чтобы старые не вытесняли кэш TDLib из лимита репозитория. Право `actions: write` есть только у этой задачи, код репозитория она не запускает.
- Архивы `FetchContent` складываются в общий каталог `TELEGA_FS_DOWNLOAD_DIR` (в пресетах `${sourceDir}/.cache/deps`, общий для всех пресетов). В CI он кэшируется по хешу `cmake/deps.cmake`. Скачанный архив повторно не загружается, если совпал его SHA256.
- Матрица сборки: `dev` и `ci` (GCC 13 и Clang 18), `asan`, `tsan` (Clang 18), `release` (GCC 13). В каждой: configure, build, `ctest` по пресету без длинных тестов (`-LE long`).
- Отдельные задачи: проверка форматирования и clang-tidy по изменённым файлам (если менялись заголовки, конфиги или сборка — по всем). clang-tidy идёт параллельно по числу ядер раннера, таймаут задачи 45 минут. Кэш результатов clang-tidy запланирован на M3 (раздел 16): ключ — хеш препроцессированного TU, флагов, `.clang-tidy` и версии clang-tidy, кэшируются только чистые результаты, пишет кэш только `main`. Там же: `ccache --zero-stats` сразу после восстановления кэша, чтобы `ccache --show-stats` в логе показывал статистику этого прогона, а не накопленную (счётчики хранятся в каталоге кэша и восстанавливаются вместе с ним).

## 17. Эксперименты

Значения, которые нельзя выбрать без замеров, выбираются экспериментами. Код, который зависит от такого значения, пишется только после отчёта и правки спеки. До этого везде действуют предварительные значения, указанные в спеке.

### 17.1 Что решается

| Эксперимент | Веха | Что фиксирует | Зависит от |
|---|---|---|---|
| E1. Размеры патчей | M1 | `max_chain`, `checkpoint_ratio` | — |
| E2. Закрепление в режиме бота | M2 | Способ поиска головы ФС (закреплённое сообщение или описание канала), минимальные права бота | — |
| E3. Чтение старых сообщений по id | M2 | Доступны ли боту `gc --deep` и `recover --scan` | — |
| E4. Скачивание диапазонов | M2 | Годится ли модель чтения из раздела 8.2, основной путь получения `file_id` | — |
| E5. Лимиты отправки | M2 | `send_rate` и `upload_concurrency` для каждого режима | — |
| E6. Альбомы | M2 | Отправляет ли TelegramStore альбомами | E5 |
| E7. Размер чанка | M2 | `chunk_size` | E4, E5, E6 |
| E8. Инлайн | M2 | `inline_max`, `inline_budget` | E1, E5 |
| E9. Пакеты | M2 | `pack_threshold`, `pack_target`, `pack_max_age` | E4, E5 |

E2 и E4 проверяют, работает ли дизайн вообще, поэтому идут первыми. Если один из них дал отрицательный ответ, остальные эксперименты M2 ждут, пока спека будет поправлена.

### 17.2 Общие правила

- **Инструменты** лежат в `tools/bench/` и собираются с опцией `TELEGA_FS_BUILD_TOOLS`:
  - `tgfs-sim` — офлайн-симуляция по спискам размеров файлов, без сети;
  - `tgfs-bench` — замеры через TdClient против тестового DC;
  - E1 гоняется на самом telega-fs с `LocalDirStore`.
- **Только тестовый DC** (`use_test_dc = true`): тестовые аккаунты и бот, заведённый у @BotFather тестового DC. Боевые серверы в экспериментах не используются.
- **Повторы.** Локальные замеры повторяются минимум 3 раза, сетевые минимум 5. В отчёт идут медиана, минимум и максимум.
- **Окружение** фиксируется в отчёте: версия TDLib, коммит telega-fs, CPU, диск, тип сети, дата и время прогона.
- **Случайность** только с фиксированным seed, seed пишется в отчёт.
- **Осторожность с лимитами.** Замер останавливается на первом `FLOOD_WAIT`: выждать указанное время с запасом и только потом продолжать. Если тестовый аккаунт заблокирован, это тоже результат: он записывается в отчёт, а серия продолжается на новом аккаунте.
- **Отчёт** — `docs/experiments/NN-<имя>.md`: цель, окружение, метод, таблицы результатов, вывод и список правок в спеке. Сырые данные лежат рядом, в `docs/experiments/NN-<имя>/*.csv`.
- **Неоднозначный результат.** Если данные не дают ясного выбора, остаётся предварительное значение из спеки (они выбраны консервативно), и это явно пишется в отчёте.

### 17.3 Наборы файлов

Наборы фиксированы и воспроизводимы, их описания и генераторы лежат в `tools/bench/corpora/`.

- **C1 «Исходники».** TDLib на коммите `ba976cb4a`: 1707 файлов, 28,9 МиБ, 62 % файлов до 4 КиБ и 35 % от 4 до 64 КиБ. Нагрузка на изменения: рабочая копия последовательно переключается между десятью коммитами из истории первого родителя `ba976cb4a`, взятыми с шагом 200.
- **C2 «Домашний каталог».** Распределение размеров снимается скриптом с реального `$HOME`, сохраняются только размеры, без имён и путей. Содержимое генерируется случайно. Список размеров коммитится как CSV.
- **C3 «Медиа».** 500 файлов от 1 до 10 МиБ (размеры равномерно) и три файла по 1, 2 и 4 ГиБ.
- **C4 «Большое дерево».** Синтетика только для индекса: 100 000 и 1 000 000 инодов, по 50 записей в каталоге; 90 % файлов в пакетах, 5 % инлайн, 5 % позиционных. При `inline_budget` 16 МиБ и 1M инодов 5 % инлайн означает в среднем не больше 335 байт на файл; генератор берёт инлайн-файлы от 16 до 600 байт.

### 17.4 E1. Размеры патчей дельта-журнала (M1, локально)

**Цель.** Убедиться, что дельта на порядки меньше снимка, а коммит дельты почти не держит блокировку. Выбрать `max_chain` и `checkpoint_ratio`.

**Метод.** telega-fs на `LocalDirStore`, после каждой нагрузки коммит:

1. распаковать C1;
2. переименовать корневой каталог C1;
3. `touch` всех файлов C1;
4. переписать 100 инлайн-файлов;
5. удалить C1;
6. собрать индекс C4 (100k и 1M) и сделать поверх 64 дельты из нагрузок 2–4.

**Метрики.**

- размер патча до и после zstd;
- время забора патча под блокировкой;
- размер снимка и время его сборки (`VACUUM INTO`, zstd, шифрование);
- время монтирования: снимок плюс применение цепочки из 8, 16, 32 и 64 дельт.

**Решение.**

- Если забор патча держит блокировку дольше 10 мс на любой нагрузке, это ошибка дизайна, раздел 6.6 пересматривается.
- `max_chain` — наибольшее значение, при котором применение цепочки на C4 (1M) занимает не больше времени скачивания и распаковки её снимка.
- `checkpoint_ratio` — лучшее из 0,1, 0,25 и 0,5 по средней стоимости коммита на нагрузках 1–5. Средняя стоимость — снимок, распределённый на цепочку, плюс дельта.
- Нужен ли нижний порог размера снимка для условия `checkpoint_ratio`. На маленьком индексе (снимок — сотни байт) при 0,25 почти каждый второй коммит становится снимком; если E1 покажет, что это заметно, вводится параметр с минимальным размером снимка, ниже которого условие не действует.

**Итог E1** (`docs/experiments/01-e1-patch-sizes.md`): `max_chain = 16`, `checkpoint_ratio = 0,25`, нижний порог снимка не нужен. Порог 10 мс превышен: забор патча на 10 000 строк при 1M инодов — 23 мс, запись патча под блокировкой — до 300 мс, `VACUUM INTO` на 1M — около 1 с. Раздел 6.6 пересмотрен: запись в `pending_patchsets` вынесена из-под блокировки, добавлен промежуточный забор по `patch_take_rows`; снимок без долгой блокировки отложен до M3.

### 17.5 E2. Закрепление в режиме бота

**Цель.** Проверить, что бот может вести голову ФС через закреплённое сообщение.

**Метод.** Канал создаёт пользователь, бот добавляется администратором сначала с полным набором прав, затем права убираются по одному. Для каждого набора прав 20 циклов подряд:

1. отправить документ;
2. `pinChatMessage` на него;
3. `getChatPinnedMessage`;
4. `unpinChatMessage` предыдущего.

Затем те же 20 циклов после перезапуска бота с пустой БД TDLib.

**Метрики.** Доля успешных циклов; видит ли `getChatPinnedMessage` новое сообщение сразу после pin; минимальный набор прав; время одного цикла.

**Решение.**

- 20 из 20 успешных циклов, включая перезапуск, — голова остаётся закреплённым сообщением, минимальные права записываются в раздел 10.3.
- Иначе голова переносится в описание канала (`setChatDescription`), раздел 7.1 переписывается, и E2 повторяется для нового варианта.

### 17.6 E3. Чтение старых сообщений по id

**Цель.** Проверить, может ли бот перебирать историю канала через `getMessages`.

**Метод.** В канале 10 000 сообщений: часть отправлена пользователем до добавления бота, часть ботом, часть удалена. Бот перебирает id от 1 до последнего пачками по 100.

**Метрики.**

- доля возвращённых существующих сообщений;
- как выглядят удалённые: пустой ответ или ошибка;
- время полного перебора;
- число и длительность `FLOOD_WAIT`.

**Решение.** Если бот видит все существующие сообщения, `gc --deep` и `recover --scan` в режиме бота работают перебором (раздел 4). Иначе в режиме бота эти две команды требуют временного входа пользователем, и это записывается в разделы 10.3 и 12.3.

### 17.7 E4. Скачивание диапазонов

**Цель.** Проверить модель чтения из раздела 8.2 в обоих режимах.

**Метод.** Документ 512 МиБ. Для каждого режима:

- скачать по 64 КиБ с начала, из середины и с конца: `downloadFile` с `offset` и `limit`, затем `readFilePart`, сверить байты с исходником;
- вызвать `getRemoteFile` по сохранённому `remote_file_id` сразу, после перезапуска с пустой БД TDLib и через 24 часа.

**Метрики.**

- время до первого байта;
- сколько TDLib скачал на самом деле (по `updateFile`): только запрошенный диапазон или больше;
- работает ли `getRemoteFile`, или нужен путь через `getMessages`.

**Решение.**

- Если частичное скачивание не работает или TDLib всегда качает файл целиком, раздел 8.2 пересматривается, а в E7 добавляется ограничение `chunk_size ≤ 8 МиБ`.
- Если `remote_file_id` протухает, путь через `getMessages` становится основным, а не запасным.

### 17.8 E5. Лимиты отправки

**Цель.** Выбрать `send_rate` и `upload_concurrency` для каждого режима.

**Метод.** Документы по 1 КиБ, 16 МиБ и 64 МиБ. Темп растёт ступенями — 5, 10, 20, 30 и 60 документов в минуту, по 10 минут на ступень — при параллельности 1, 2 и 4. Ступень обрывается на первом `FLOOD_WAIT`. Отдельная серия: после `FLOOD_WAIT` выждать 30 минут и проверить, вернулся ли прежний темп.

**Метрики.**

- наибольший темп, на котором за 10 минут не было `FLOOD_WAIT`;
- длительность `FLOOD_WAIT`;
- зависимость от размера документа и параллельности.

**Решение.**

- `send_rate` — 70 % от наибольшего устойчивого темпа для данного режима.
- `upload_concurrency` — наименьшая параллельность, при которой скорость заливки документов по 16 МиБ выходит на плато.

### 17.9 E6. Альбомы

**Цель.** Понять, стоит ли отправлять чанки альбомами.

**Метод.** Повторить E5 для документов по 16 МиБ, отправляя их `sendMessageAlbum` по 10 штук. Отдельно отправить альбом, в котором один документ заведомо не уйдёт (например, его локальный файл удалён до отправки).

**Метрики.**

- документов в минуту без `FLOOD_WAIT` по сравнению с одиночной отправкой;
- приходит ли `updateMessageSendSucceeded` или `updateMessageSendFailed` на каждый документ альбома отдельно;
- что происходит с остальными документами, если один не отправился.

**Решение.** Альбомы используются, если дают как минимум в 1,5 раза больше документов в минуту и сбой одного документа не ломает остальные. Иначе TelegramStore отправляет по одному документу.

### 17.10 E7. Размер чанка

**Цель.** Выбрать `chunk_size`.

**Метод.** Чанки 8, 16, 32 и 64 МиБ, оба режима, набор C3, `send_rate` и способ отправки по итогам E5 и E6:

- заливка 2 ГиБ;
- скачивание тех же 2 ГиБ с холодным кэшем;
- 100 перезаписей по 4 КиБ в случайных местах файла 1 ГиБ.

**Метрики.**

- эффективная скорость заливки и скачивания в МиБ/с с учётом `send_rate`;
- сообщений на ГиБ;
- среднее время read-modify-write одной перезаписи.

**Решение.** Наименьший размер, при котором эффективная скорость заливки не ниже 80 % от максимальной среди проверенных. Если по этому критерию подходят несколько размеров, берётся тот, у которого дешевле read-modify-write.

### 17.11 E8. Инлайн

**Цель.** Выбрать `inline_max` и `inline_budget`.

**Метод.** Пороги `inline_max` 0, 1, 2, 4, 8 и 16 КиБ, бюджеты `inline_budget` 4, 16 и 64 МиБ, наборы C1, C2 и C4. Коммиты идут по `commit_interval`, с дельта-журналом и `max_chain` из E1.

**Метрики.**

- размер снимка после zstd и шифрования;
- время сборки и заливки снимка на тестовом DC;
- размер типичной дельты при правке инлайн-файлов;
- сколько сообщений экономит инлайн.

**Решение.** При заполненном бюджете средняя стоимость коммита (снимок, распределённый на цепочку, плюс типичная дельта) не больше 10 % от `commit_interval`. Среди подходящих вариантов берётся тот, что экономит больше всего сообщений.

### 17.12 E9. Пакеты

**Цель.** Выбрать `pack_threshold`, `pack_target` и `pack_max_age`.

**Метод.**

- Офлайн в `tgfs-sim` на C1 и C2: `pack_threshold` 64 КиБ, 256 КиБ, 1 МиБ и 4 МиБ; `pack_target` 4, 16 и 64 МиБ; `pack_max_age` 10, 30 и 120 с. На C1 плюс нагрузка с переключением коммитов.
- На тестовом DC: холодное чтение файлов по 2, 32 и 512 КиБ из пакетов 4, 16 и 64 МиБ по сравнению с отдельным маленьким документом того же размера.

**Метрики.**

- число сообщений на заливку набора;
- доля мёртвого места после нагрузки;
- доля недобранных пакетов, закрытых по `fsync` или `pack_max_age`;
- задержка холодного чтения.

**Решение.**

- `pack_threshold` — наибольший порог, при котором холодное чтение файла из пакета медленнее чтения отдельного документа не больше чем в 1,5 раза.
- `pack_target` — наибольший размер, при котором задержка холодного чтения растёт не больше чем на 20 % относительно пакета 4 МиБ.
- `pack_max_age` — наименьшее значение, при котором на C1 недобранных пакетов не больше 20 %.
